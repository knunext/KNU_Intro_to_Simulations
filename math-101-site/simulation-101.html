평균만으로는 줄이 안 보인다: 결정적 모형과 확률적 모형

쓰인 곳물류창고 로봇의 충전데이터센터의 작업 대기열확률과 통계 101 7단계의 지수분포로켓 시뮬레이션의 바람과 엔진 잡음
먼저, 수식 없이

물류창고 로봇들이 충전기 하나를 나눠 씁니다. 로봇은 평균 10분마다 한 대씩 오고, 충전은 평균 8분 걸려요. 충전기는 80%의 시간만 바쁘니 줄이 생길 리 없어 보입니다. 정말로 로봇이 정확히 10분마다 오고 정확히 8분씩 충전한다면 그렇습니다. 줄은 영원히 0이에요.

그런데 실제 도착은 들쭉날쭉합니다. 3분 간격으로 두 대가 오기도 하고 25분 동안 한 대도 안 오기도 해요. 그러면 몰려온 순간에 줄이 생기고, 한산한 순간에는 충전기가 놀면서 그 시간을 되찾지 못합니다. 같은 평균인데 평균 대기 시간이 0분에서 30분 넘게로 바뀌어요.

그래서 모형을 세울 때 첫 질문은 ‘무엇을 무작위로 둘 것인가’입니다. 무작위를 무시한 결정적 모형은 계산이 쉽지만 줄, 고장, 지연처럼 ‘가끔 몰려서 생기는 일’을 보지 못해요. 무작위를 넣은 확률적 모형은 돌릴 때마다 답이 달라서, 결과를 읽는 법(3부)이 따로 필요합니다.

한 줄로평균이 같아도 무작위가 있으면 줄이 생깁니다. 결정적 모형은 이걸 못 보고, 확률적 모형은 보지만 결과를 통계로 읽어야 해요.

결정적 모형 xk+1 = f(xk)는 같은 출발점에서 늘 같은 궤적을 냅니다. 확률적 모형 xk+1 = f(xk, ξk)는 무작위 입력 ξ가 섞여 있어 한 번 돌린 결과는 ‘가능한 결과 중 하나’일 뿐이에요. 질문도 ‘몇 분 기다리나’에서 ‘평균 몇 분, 95%의 경우 몇 분 이하’로 바뀝니다.

대기행렬에서 무작위가 줄을 만드는 이유는 비대칭 때문입니다. 충전기가 놀았던 시간은 저장해 둘 수 없지만, 몰려온 로봇은 줄에 쌓여 다음으로 넘어가요. 그래서 이용률 ρ가 1에 가까워질수록 평균 대기 시간이 1/(1 − ρ)에 비례해 폭발합니다(5단계). 결정적 모형에서는 ρ < 1이기만 하면 대기가 0이에요.

무엇을 무작위로 두느냐는 모형을 쓰는 목적이 정합니다. 로켓의 착지 정확도를 보려면 바람과 엔진 추력의 흔들림을, 위성 군집의 가용도를 보려면 고장 시각과 수리 시간을 무작위로 둬야 해요. 반대로 목적과 상관없는 무작위까지 넣으면 결과만 흐려집니다.

결정적 모형과 확률적 모형
(1)
  1. 1결정적 모형. 다음 상태가 지금 상태로만 정해져요.
  2. 2확률적 모형. 무작위 입력 ξ가 섞여 돌릴 때마다 결과가 다릅니다.
  3. 3이용률. 0.8이면 평균으로는 20% 여유. 그래도 무작위면 줄이 생겨요.
파이썬
import numpy as np
rng = np.random.default_rng(1)

def charger(inter, service):                 # 충전기 하나, 먼저 온 순서대로
    t_arr = np.cumsum(inter)                  # 도착 시각
    free_at, waits = 0.0, []
    for a, s in zip(t_arr, service):
        start = max(a, free_at)               # 충전기가 비면 바로, 아니면 기다림
        waits.append(start - a)
        free_at = start + s
    return np.mean(waits)

n = 50_000
print(charger(np.full(n, 10.0), np.full(n, 8.0)))                      # 0.0
print(charger(rng.exponential(10, n), rng.exponential(8, n)))          # 약 32
print(charger(rng.exponential(10, n), np.full(n, 8.0)))                # 약 16 (도착만 무작위)

시계를 어떻게 넘길까: 고정 간격과 사건 진행

쓰인 곳미적분 101 12단계의 시간 칸 Δt수치해석 101 10단계의 사건 찾기위성 소프트 에러네트워크 패킷 시뮬레이터
먼저, 수식 없이

미적분 101의 시뮬레이터는 Δt마다 시계를 한 칸씩 넘기며 ‘지금 무슨 일이 있나’를 확인했습니다(고정 간격). 공의 위치처럼 끊임없이 변하는 것에는 자연스러운 방법이에요.

그런데 위성에 방사선 소프트 에러가 하루에 몇 번 생기는지, 충전기에 로봇이 언제 도착하는지처럼 ‘가끔 일어나는 사건’에는 비효율적입니다. Δt를 크게 잡으면 사건을 늦게 알아채고 같은 칸에 든 두 사건의 순서를 잃고, 작게 잡으면 아무 일도 없는 칸을 수백만 번 확인해요.

사건 진행 방식은 시계를 다음 사건의 시각으로 바로 건너뜁니다. 사건과 사건 사이에는 상태가 변하지 않으니 확인할 필요가 없어요. 사건이 드물수록 수천 배 빨라지고, 사건 시각도 정확합니다. 이 페이지의 시뮬레이터는 모두 이 방식이에요.

한 줄로고정 간격은 Δt마다 확인해서 사건을 늦게 알아채고 빈 칸을 낭비합니다. 사건 진행은 다음 사건 시각으로 바로 건너뛰어 정확하고 빨라요.

고정 간격 시뮬레이션은 tk+1 = tk + Δt로 진행하며, 칸 안에서 일어난 사건을 칸 끝에서 처리합니다. 그래서 사건마다 최대 Δt만큼 늦게 반영되고, 한 칸에 사건이 둘 이상이면 실제 순서를 알 수 없어요. 계산량은 시뮬레이션 시간 ÷ Δt로, 사건이 몇 개든 같습니다.

사건 진행 시뮬레이션은 앞으로 일어날 사건들을 시각과 함께 목록에 넣어 두고, 가장 이른 것을 꺼내 시계를 그 시각으로 옮긴 뒤 처리합니다. 처리하면서 생기는 새 사건(다음 도착, 충전 끝)을 다시 목록에 넣고요. 계산량은 사건 수에 비례하고, 시각은 부동소수점 정밀도까지 정확해요.

두 방식은 섞어 쓰기도 합니다. 로봇의 움직임은 고정 간격으로 적분하고, 충돌·고장·통신 메시지 같은 사건은 사건 목록으로 처리하는 혼합 시뮬레이션이에요. MuJoCo 같은 물리 엔진과 네트워크 시뮬레이터를 함께 돌리는 공동 시뮬레이션이 이런 구조입니다.

시간을 넘기는 두 방식
(2)
  1. 1고정 간격. 칸마다 확인. 사건은 최대 Δt 늦게 반영되고 같은 칸의 순서는 사라져요.
  2. 2사건 진행. 목록에서 가장 이른 사건 시각으로 시계를 바로 옮깁니다.
파이썬
import numpy as np
rng = np.random.default_rng(2)

events = np.cumsum(rng.exponential(5.0, 12))     # 평균 5시간마다 소프트 에러
events = events[events < 60]

dt = 2.0                                          # 고정 간격: 2시간마다 확인
seen_at = np.ceil(events / dt) * dt
print('늦게 알아챈 시간(평균):', np.mean(seen_at - events))
print('같은 칸에 겹친 사건:', len(events) - len(np.unique(seen_at)))

t = 0.0                                           # 사건 진행: 다음 사건으로 점프
for te in events:
    t = te                                        # 시계 = 사건 시각, 지연 0

사건 목록 하나로 시뮬레이터 짜기

먼저, 수식 없이

사건 진행 시뮬레이터의 심장은 사건 목록입니다. ‘12.4분에 로봇 도착’, ‘15.0분에 충전 끝’처럼 앞으로 일어날 사건을 시각과 함께 담아 두는 목록이에요. 시뮬레이터는 같은 일을 되풀이합니다. 가장 이른 사건을 꺼내고, 시계를 그 시각으로 옮기고, 상태를 바꾸고, 그 결과로 생기는 새 사건을 목록에 넣기.

충전기 예라면 사건은 두 종류뿐입니다. ‘도착’이 꺼내지면 다음 도착을 하나 예약하고, 충전기가 비었으면 충전을 시작하며 ‘충전 끝’을 예약하고, 바쁘면 줄에 세워요. ‘충전 끝’이 꺼내지면 줄의 맨 앞 로봇을 충전기에 올리고 그 로봇의 ‘충전 끝’을 예약합니다.

‘가장 이른 것을 꺼내기’와 ‘아무 시각이나 넣기’를 빠르게 하는 자료구조가 자료구조 수업의 우선순위 큐(힙)예요. 사건이 n개 있어도 꺼내기와 넣기가 log n번이면 끝납니다. 통계는 사건이 일어날 때마다 ‘지난 사건부터 지금까지 줄에 몇 대가 있었나 × 그 시간’을 더해 두면 나와요.

한 줄로사건 진행 시뮬레이터는 ‘가장 이른 사건 꺼내기 → 시계 옮기기 → 상태 바꾸기 → 새 사건 넣기’의 되풀이입니다. 사건 목록은 우선순위 큐로 만들어요.

사건 목록
앞으로 일어날 사건과 시각을 담은 우선순위 큐.
상태
시뮬레이션의 지금 모습. 줄의 길이, 충전기의 바쁨.
사건 처리기
사건 종류마다 상태를 바꾸고 새 사건을 예약하는 코드.
시간 평균
값 × 머문 시간을 더해 전체 시간으로 나눈 평균.

까먹었다면자료구조·알고리즘의 힙: 부모가 자식보다 작은 완전 이진 트리. 가장 작은 원소가 늘 뿌리에 있고, 꺼내기·넣기가 O(log n)이에요.

조금 더 정확하게

한 바퀴는 (t, e) ← pop(Q), 시계 ← t, 처리기(e)가 상태를 바꾸고 새 사건을 push(Q)입니다. 시각이 같은 사건은 넣은 순서로 처리해 결과가 늘 같게 해요(재현성). 끝내는 조건은 시각(T분까지), 사건 수(로봇 N대까지), 또는 목록이 비었을 때입니다.

통계는 두 종류입니다. 로봇마다 기다린 시간의 평균 같은 관측 평균은 충전을 시작할 때 (시작 시각 − 도착 시각)을 더해 두면 되고, 줄의 평균 길이 같은 시간 평균은 L̄ = (1/T)∫N(t)dt, 곧 사건과 사건 사이 구간마다 N × 구간 길이를 더해 T로 나눕니다. N이 사건 사이에서는 변하지 않으니 적분이 합이 돼요(미적분 101 10단계의 리만 합이 이 경우 정확합니다).

실제로는 파이썬의 heapq로 몇십 줄이면 짤 수 있고, SimPy 같은 라이브러리는 사건 목록을 감추고 ‘로봇은 도착해서, 충전기를 요청하고, 기다렸다가, 충전한다’처럼 과정을 그대로 적게 해 줍니다. 그래도 속에서는 같은 사건 목록이 돌아요.

사건 진행 시뮬레이션의 한 바퀴
(3)
  1. 1가장 이른 사건 꺼내기. 힙의 뿌리. 시계를 그 시각으로 옮겨요.
  2. 2처리하고 예약하기. 상태를 바꾸고, 그 때문에 생기는 미래의 사건을 넣습니다.
  3. 3시간 평균. 사건 사이에는 N이 일정하니 적분이 정확히 합이 돼요.
파이썬
import heapq, random
random.seed(3)
lam, mu, N = 1/10, 1/8, 10_000

Q = [(random.expovariate(lam), 0, 'arr')]   # (시각, 순번, 종류)
seq, t, busy, line = 1, 0.0, False, []
waits, area, last = [], 0.0, 0.0
while Q:
    t_new, _, kind = heapq.heappop(Q)       # 가장 이른 사건
    area += len(line) * (t_new - last); last = t = t_new
    if kind == 'arr':
        if len(waits) + len(line) + busy < N:
            heapq.heappush(Q, (t + random.expovariate(lam), seq, 'arr')); seq += 1
        if not busy:
            busy = True; waits.append(0.0)
            heapq.heappush(Q, (t + random.expovariate(mu), seq, 'dep')); seq += 1
        else:
            line.append(t)
    else:                                    # 충전 끝
        if line:
            waits.append(t - line.pop(0))
            heapq.heappush(Q, (t + random.expovariate(mu), seq, 'dep')); seq += 1
        else:
            busy = False
print(sum(waits) / len(waits), area / t)    # 평균 대기(약 32), 평균 줄 길이(약 3.2)

시뮬레이터에 ‘충전 시간은 무작위’라고 넣으려면 어떤 무작위인지, 곧 분포를 정해야 합니다. 현장에서 잰 충전 시간 200개가 있다고 해 봅시다. 평균은 6.7분이에요. 그럼 평균 6.7분인 지수분포를 넣으면 될까요?

분포는 평균만으로 정해지지 않습니다. 같은 평균 6.7분이라도 지수분포는 1분 미만으로 끝나는 경우가 많고 가끔 20분이 넘는데, 실제 충전은 4~9분에 몰려 있을 수 있어요. 엉뚱한 분포를 넣으면 시뮬레이터는 정교해도 결과는 틀립니다(쓰레기를 넣으면 쓰레기가 나온다).

한 줄로입력 분포는 평균이 아니라 모양까지 맞춰야 합니다. 후보 분포를 데이터에 맞추고 히스토그램, Q-Q 그림, K-S 거리로 비교해 고르세요.

조금 더 정확하게

지수분포는 평균 하나로 정해지고 최대 가능도 추정값은 표본 평균입니다. 정규분포는 평균과 표준편차, 로그정규분포는 ln x의 평균과 표준편차예요. 시간이나 크기처럼 0보다 크고 오른쪽 꼬리가 긴 값에는 로그정규나 감마, 와이블 분포가, 사건 사이 시간에는 지수분포가 자주 맞습니다. 정규분포는 음수가 나올 수 있어서 시간에 쓸 때 조심해야 해요.

K-S 통계량 D = max|Fn(x) − F(x)|는 데이터의 계단 모양 누적 분포 Fn과 후보 분포 F가 가장 크게 벌어진 거리입니다. 표본이 n개일 때 D가 대략 1.36/√n보다 크면 ‘이 분포에서 나온 데이터라고 보기 어렵다’고 해요(5% 기준). 다만 모수를 같은 데이터로 추정했으면 이 기준은 조금 너그러워서, 실제로는 Q-Q 그림을 함께 봅니다.

데이터가 없거나 적으면 전문가의 최솟값·최빈값·최댓값으로 삼각분포를 쓰고, 데이터가 많으면 분포를 고르지 않고 데이터에서 그대로 뽑는(경험 분포) 방법도 있어요. 어떤 경우든 입력 가정이 결과를 얼마나 바꾸는지 9단계의 민감도 점검으로 확인합니다.

분포 맞추기와 K-S 거리
(4)
  1. 1모수 추정. 지수분포는 평균, 로그정규는 로그를 씌운 값의 평균과 표준편차. 둘 다 최대 가능도 추정값이에요.
  2. 2K-S 거리. 누적 분포가 가장 크게 벌어진 곳. 1.36/√n을 넘으면 그 분포를 의심합니다.
파이썬
import numpy as np
from scipy import stats

data = np.random.default_rng(9).lognormal(1.8, 0.45, 200)   # '현장' 충전 시간
cands = {
    '지수':     stats.expon(scale=data.mean()),
    '정규':     stats.norm(data.mean(), data.std(ddof=1)),
    '로그정규': stats.lognorm(s=np.log(data).std(ddof=1), scale=np.exp(np.log(data).mean())),
}
for name, dist in cands.items():
    D = stats.kstest(data, dist.cdf).statistic
    print(name, round(D, 3), '기준', round(1.36 / np.sqrt(len(data)), 3))
# 지수 0.32 (크게 벗어남), 정규 0.08, 로그정규 0.04

q_data = np.sort(data)                                       # Q-Q 그림의 점들
q_model = cands['로그정규'].ppf((np.arange(200) + 0.5) / 200)

  • [표본 수]를 30으로 줄이면 기준선이 높아져서 정규분포도 로그정규분포도 ‘기각 안 됨’이 됩니다. 데이터가 적으면 분포를 가려내기 어렵다는 뜻이에요. 그럴수록 9단계의 민감도 점검이 중요합니다.

가장 단순한 줄 서기의 공식: M/M/1과 리틀의 법칙

쓰인 곳물류창고 충전기데이터센터 작업 큐다중 로봇 경로 계획(MAPF)의 병목9단계의 검증 기준

도착이 무작위(지수분포 간격), 처리 시간도 무작위(지수분포), 서버가 하나인 줄을 M/M/1 대기행렬이라고 부릅니다. 이렇게 단순한 경우에는 시뮬레이션 없이도 평균 줄 길이와 대기 시간을 식 하나로 구할 수 있어요.

결과는 놀랍습니다. 이용률 ρ가 0.5면 평균 대기는 처리 시간과 같은 수준인데, 0.8이면 처리 시간의 4배, 0.9면 9배, 0.99면 99배예요. 서버가 조금만 더 바빠져도 줄은 폭발합니다. 그래서 실제 시스템은 이용률을 70~80% 아래로 설계해요.

그리고 거의 모든 줄에 성립하는 아름다운 법칙이 하나 있습니다. 리틀의 법칙 L = λW. 시스템 안의 평균 대수 = 1분에 들어오는 대수 × 한 대가 머무는 평균 시간. 분포가 무엇이든, 서버가 몇 개든 성립해서, 시뮬레이터가 맞게 도는지 확인하는 기준(9단계)으로도 씁니다.

한 줄로M/M/1에서는 L = ρ/(1 − ρ)처럼 이용률 ρ가 1에 다가갈수록 줄이 폭발합니다. 리틀의 법칙 L = λW는 거의 모든 줄에 성립해요.

M/M/1은 확률과 통계 101 12단계의 마르코프 연쇄로 풀립니다. 시스템 안 대수 n을 상태로 두면, n에서 n + 1로는 λ, n에서 n − 1로는 μ의 비율로 옮겨 가요. 정상 상태에서 이웃 상태 사이의 흐름이 균형을 이루면 pn = (1 − ρ)ρⁿ이고, 평균을 내면 L = ρ/(1 − ρ), W = 1/(μ − λ), 줄에서만 기다리는 시간은 Wq = ρ/(μ − λ)입니다. ρ = 0.8, 처리 8분이면 Wq = 32분이에요.

리틀의 법칙은 오래 관찰한 어떤 시스템에서든 ‘시간 평균 대수 = 도착률 × 관측 평균 체류 시간’이 성립한다는 정리입니다. 줄에만 적용하면 Lq = λWq, 충전기에만 적용하면 ‘바쁜 충전기 수 = λ × 평균 충전 시간 = ρ’예요. 셋 중 둘을 재면 나머지가 나오니, 시뮬레이터의 통계가 서로 앞뒤가 맞는지 확인하는 데 아주 좋습니다.

대부분의 실제 시스템은 M/M/1보다 복잡해서(서버 여럿, 우선순위, 네트워크로 이어진 줄, 지수분포가 아닌 처리 시간) 식이 없거나 근사뿐입니다. 그래서 시뮬레이션을 하지만, 이 단순한 공식은 시뮬레이터를 검증하는 기준점이자 ‘어디가 병목인가’를 어림하는 도구로 계속 쓰여요.

(5)

import numpy as np

mu = 1 / 8                                   # 8분에 한 대 충전
for rho in [0.5, 0.8, 0.9, 0.95]:
    lam = rho * mu
    L  = rho / (1 - rho)                     # 시스템 안 평균 대수
    Wq = rho / (mu - lam)                    # 줄에서 기다리는 평균 시간
    W  = 1 / (mu - lam)                      # 시스템에 머무는 평균 시간
    print(rho, round(L, 2), round(Wq, 1), np.isclose(L, lam * W))   # 리틀의 법칙

한 번 돌린 결과는 믿을 수 없다: 반복 실험과 신뢰구간

쓰인 곳확률과 통계 101 21단계의 t분포로켓 착지 몬테카를로강화학습의 여러 시드 평가8단계의 설계 비교
먼저, 수식 없이

확률적 시뮬레이터를 한 번 돌려 ‘평균 대기 29분’이 나왔습니다. 다시 돌리면 35분, 또 돌리면 31분. 어느 게 답일까요? 어느 것도 아닙니다. 한 번의 결과는 ‘가능한 결과 중 하나’일 뿐이에요.

그래서 다른 난수로 여러 번 독립적으로 돌리고(반복 실험), 그 결과들의 평균과 퍼짐으로 ‘참값이 이 범위에 있을 것’이라는 신뢰구간을 말합니다. 반복을 4배로 늘리면 구간 폭이 절반이 돼요. 확률과 통계 101의 1/√n 그대로입니다.

95% 신뢰구간은 ‘이런 실험을 100번 하면 그중 약 95번은 구간이 참값을 품는다’는 뜻이에요. 실습에서 신뢰구간 100개를 한꺼번에 만들어, 참값을 놓친 구간이 몇 개인지 직접 세어 봅니다. 강화학습 결과를 여러 시드로 평가하는 것도 같은 이유예요.

한 줄로확률적 시뮬레이션은 다른 난수로 R번 반복해 평균 ± t·s/√R로 신뢰구간을 냅니다. 폭은 1/√R로 줄고, 95% 구간은 100번 중 약 95번 참값을 품어요.

R번 반복한 결과 X1, …, XR은 서로 독립이고 같은 분포를 따르므로, 평균 X̄의 표준오차는 s/√R이고 95% 신뢰구간은 X̄ ± tR−1, 0.975·s/√R입니다. 한 번의 실행 안에서 로봇 수천 대의 대기를 평균 낸 값을 그대로 쓰면 안 되는 이유는 7단계에서 봐요. 한 실행 안의 값들은 서로 독립이 아니거든요.

원하는 정밀도가 있으면 반복 횟수를 거꾸로 정합니다. 처음 R₀번 돌려 s를 어림하고, 반폭을 h로 줄이려면 R ≈ (t·s/h)²번이 필요해요. 반폭을 절반으로 줄이려면 4배를 돌려야 하니, 정밀도는 비쌉니다. 그래서 8단계의 분산 줄이기 기법이 중요해요.

포함률이 95%보다 조금 모자랄 때가 많습니다. 대기 시간처럼 오른쪽으로 치우친 결과를 적은 반복으로 평균 내면 t분포 가정이 살짝 어긋나기 때문이에요. 이 실습의 설정에서는 대략 90~93%가 나옵니다. 반복을 늘리면 95%에 다가가요.

반복 실험의 신뢰구간
(6)
  1. 1반복의 평균. 각 Xr은 한 번의 실행 전체에서 낸 결과(예: 그 실행의 평균 대기).
  2. 295% 신뢰구간. 반폭은 √R에 반비례. 정밀도를 두 배로 하려면 네 배를 돌려야 해요.
파이썬
import numpy as np
from scipy import stats

def one_run(rng, n=2000, lam=1/10, mu=1/8):          # 한 번의 실행 → 평균 대기
    a = np.cumsum(rng.exponential(1/lam, n)); s = rng.exponential(1/mu, n)
    free, w = 0.0, np.empty(n)
    for i in range(n):
        start = max(a[i], free); w[i] = start - a[i]; free = start + s[i]
    return w[200:].mean()                              # 앞부분은 버림 (7단계)

R = 10
X = np.array([one_run(np.random.default_rng(seed)) for seed in range(R)])
h = stats.t.ppf(0.975, R - 1) * X.std(ddof=1) / np.sqrt(R)
print(f'{X.mean():.1f} ± {h:.1f} 분  (이론 32.0)')

R_need = (stats.t.ppf(0.975, R - 1) * X.std(ddof=1) / 1.0) ** 2   # 반폭 1분이 되려면
print(int(np.ceil(R_need)), '번')

처음 구간은 버린다: 워밍업, 자기상관, 배치 평균

쓰인 곳5단계의 정상 상태6단계의 반복 실험강화학습의 학습 곡선확률과 통계 101의 따라가는 평균
먼저, 수식 없이

시뮬레이터는 보통 ‘충전기도 비고 줄도 없는’ 상태에서 시작합니다. 그런데 우리가 알고 싶은 건 하루 종일 돌아가는 창고의 평균 모습이에요. 처음 얼마 동안은 줄이 실제보다 짧아서, 그 구간까지 평균에 넣으면 대기 시간을 과소평가합니다. 그래서 처음 구간을 버려요(워밍업).

얼마나 버릴지는 그림으로 정합니다. 여러 번 반복한 실행의 줄 길이를 시각마다 평균 내어 매끄럽게 그리면, 처음에 오르다가 평평해지는 지점이 보여요. 그 지점까지를 버립니다. 붐빌수록 평평해지는 데 오래 걸려요.

한 번의 긴 실행으로 신뢰구간을 내고 싶을 수도 있습니다. 그런데 한 로봇이 오래 기다렸으면 바로 뒤 로봇도 오래 기다릴 가능성이 커서, 연속한 값들은 독립이 아니에요(자기상관). 그대로 6단계의 공식을 쓰면 구간이 실제보다 훨씬 좁게 나옵니다. 긴 실행을 큰 덩어리(배치) 몇 개로 잘라 덩어리의 평균끼리 신뢰구간을 내는 배치 평균이 처방이에요.

한 줄로빈 상태에서 시작한 처음 구간은 편향되어 있으니 버립니다. 한 실행 안의 값들은 자기상관이 있어서, 신뢰구간은 반복이나 배치 평균으로 내야 해요.

조금 더 정확하게

워밍업을 버리면 X̄ = (1/(n − d))Σi>d Xi로 평균을 냅니다. d가 너무 작으면 편향이 남고, 너무 크면 데이터를 낭비해 분산이 커져요. Welch 방법은 R개 반복의 i번째 값들을 평균 낸 곡선에 이동 평균을 씌워 평평해지는 지점을 눈으로 찾습니다. M/M/1에서 ρ가 클수록 정상 상태에 닿는 시간이 대략 1/(μ(1 − √ρ)²)로 길어져요.

연속한 대기 시간의 자기상관 ρk = corr(Xi, Xi+k)는 붐빌수록 크고 천천히 줄어듭니다. 값들이 양의 상관을 가지면 n개의 정보량은 독립 표본 n개보다 훨씬 적어서, s/√n은 실제 오차를 몇 배 과소평가해요. 실습의 ‘단순 구간’이 참값을 자주 놓치는 이유입니다.

배치 평균은 워밍업 뒤의 긴 실행을 b개(보통 10~30개)의 배치로 자릅니다. 배치가 충분히 길면 배치 평균끼리는 거의 독립이라 6단계의 공식을 쓸 수 있어요. 반복 실험(매번 워밍업을 버려야 함)과 배치 평균(워밍업을 한 번만 버림) 중 무엇이 나은지는 워밍업 길이에 달렸습니다.

워밍업과 배치 평균
(7)

  2. 2자기상관. k칸 떨어진 값끼리의 상관. 붐빌수록 크고 오래 남아요.

import numpy as np
from scipy import stats

def waits(rng, n, lam=0.9/8, mu=1/8):                 # rho = 0.9, 빈 상태에서 시작
    a = np.cumsum(rng.exponential(1/lam, n)); s = rng.exponential(1/mu, n)
    free, w = 0.0, np.empty(n)
    for i in range(n):
        st = max(a[i], free); w[i] = st - a[i]; free = st + s[i]
    return w

W = np.array([waits(np.random.default_rng(k), 1500) for k in range(100)])
welch = np.convolve(W.mean(0), np.ones(101) / 101, mode='valid')   # 평평해지는 곳 찾기
d = 400                                                  # 그림을 보고 정한 워밍업

x = waits(np.random.default_rng(99), 200_000)[d:]
naive = 1.96 * x.std() / np.sqrt(len(x))                # 독립이라고 가정 (틀림)
B = x[: len(x) // 20 * 20].reshape(20, -1).mean(1)      # 배치 20개
h = stats.t.ppf(0.975, 19) * B.std(ddof=1) / np.sqrt(20)
print(x.mean(), naive, h)                               # 배치 구간이 몇 배 넓다

  • 오른쪽에서 ‘워밍업 포함 평균’과 ‘잘라 낸 평균’을 이론값과 비교하세요. 워밍업을 0으로 두면 짧은 실행에서 평균이 이론값보다 확연히 작습니다(편향).
  • 아래 막대는 연속한 대기 시간의 자기상관입니다. ρ가 클수록 막대가 오래 높게 남아요. 그때 ‘단순 구간’의 반폭이 ‘배치 평균 구간’보다 몇 배 좁게, 곧 근거 없이 자신 있게 나옵니다.

충전기를 더 빠른 모델(평균 7.5분)로 바꾸면 대기가 얼마나 줄까요? 두 설계를 각각 10번씩 돌려 비교하면, 차이가 우연인지 진짜인지 가리기 어려울 만큼 구간이 넓게 나옵니다. 운 좋게 한산한 날과 운 나쁘게 붐비는 날이 섞여 들어가서요.

해법은 두 설계를 같은 날에 시험하는 겁니다. 시뮬레이션에서는 가능해요. 같은 시드로 같은 도착 시각들과 같은 ‘충전 난이도’를 만들어 두 설계에 똑같이 넣으면(공통 난수), 붐비는 날은 두 설계 모두 붐비고 한산한 날은 둘 다 한산합니다. 그러면 차이에서 날씨 같은 운이 상쇄돼요.

이렇게 하려면 난수를 ‘용도별로’ 따로 만들어야 합니다. 도착용 난수열과 충전용 난수열을 다른 시드로 분리해 두면, 설계를 바꿔도 같은 로봇은 같은 시각에 오고 같은 비율로 오래 충전해요. 난수 시드를 관리하는 습관이 비교의 정밀도를 결정합니다.

한 줄로두 설계를 비교할 때 같은 난수열을 넣으면 운이 상쇄되어 차이의 신뢰구간이 크게 좁아집니다. 난수를 용도별로 분리해 두는 것이 전제예요.

독립적으로 돌리면 Cov(XA, XB) = 0이라 차이의 분산은 Var XA + Var XB입니다. 공통 난수를 쓰면 두 결과가 같은 방향으로 흔들려 공분산이 크게 양수가 되고, 차이의 분산이 몇 분의 일로 줄어요. 같은 반복 횟수로 구간이 몇 배 좁아지니, 같은 정밀도라면 계산이 몇십 분의 일로 줄어드는 셈입니다.

효과를 보려면 ‘같은 무작위가 같은 역할’을 하게 맞춰야 해요(동기화). 충전 시간을 역변환으로 만들면 s = −m·ln U에서 U를 같게 두고 평균 m만 바꾸면, 오래 걸리는 로봇은 두 설계에서 모두 오래 걸립니다. 도착 흐름과 충전 흐름을 섞어 한 난수열에서 뽑으면, 설계에 따라 꺼내는 순서가 달라져 동기화가 깨져요.

공통 난수 말고도 분산 줄이기 기법이 몇 가지 있습니다. U와 1 − U를 짝지어 쓰는 대조 변수, 답을 아는 비슷한 양으로 보정하는 제어 변수, 드문 사건(로켓 엔진 고장 같은)을 일부러 자주 일어나게 하고 무게로 되돌리는 중요도 표본추출이에요. 모두 ‘같은 계산으로 더 좁은 구간’을 목표로 합니다.

파이썬
import numpy as np
from scipy import stats

def run(u_arr, u_srv, m_srv, lam=1/10):               # 난수를 밖에서 받는다
    a = np.cumsum(-np.log(u_arr) / lam)
    s = -m_srv * np.log(u_srv)                          # 역변환: 같은 U → 같은 순위
    free, w = 0.0, np.empty(len(a))
    for i in range(len(a)):
        st = max(a[i], free); w[i] = st - a[i]; free = st + s[i]
    return w[200:].mean()

R, n = 10, 1000
d_ind, d_crn = [], []
for r in range(R):
    ga, gs = np.random.default_rng(100 + r), np.random.default_rng(200 + r)   # 흐름 분리
    ua, us = ga.random(n), gs.random(n)
    d_crn.append(run(ua, us, 8.0) - run(ua, us, 7.5))                         # 같은 날
    gb = np.random.default_rng(300 + r)
    d_ind.append(run(ua, us, 8.0) - run(gb.random(n), gb.random(n), 7.5))     # 다른 날
for name, d in [('독립', d_ind), ('공통 난수', d_crn)]:
    h = stats.t.ppf(0.975, R - 1) * np.std(d, ddof=1) / np.sqrt(R)
    print(name, round(np.mean(d), 1), '±', round(h, 1))

  • 위 산점도의 점은 반복마다 (설계 A의 결과, 설계 B의 결과)입니다. 공통 난수에서는 점들이 대각선 근처에 늘어서요(강한 양의 상관). 독립에서는 퍼져 있습니다. 오른쪽의 상관계수를 보세요.
  • [흐름 섞기]를 켜면 도착과 충전을 한 난수열에서 번갈아 뽑습니다. 같은 시드인데도 상관이 약해지고 구간이 다시 넓어져요. 난수를 용도별로 나눠야 하는 이유입니다.

핵심

두 설계를 비교할 때는 같은 난수를 같은 역할로 넣어(공통 난수) 운을 상쇄하세요. 차이의 구간이 몇 배 좁아집니다. 난수를 용도별 흐름으로 나누는 것이 전제예요.

코드는 모형대로, 모형은 현실대로: 검증과 확인

쓰인 곳5단계의 리틀의 법칙6단계의 신뢰구간수치해석 101의 수렴 검증로봇 시뮬레이터와 실제 로봇의 차이(sim-to-real)
먼저, 수식 없이

시뮬레이터가 그럴듯한 숫자를 냈다고 믿어도 될까요? 두 가지를 따로 물어야 합니다. 하나는 검증(verification), ‘코드가 내가 의도한 모형대로 도는가?’예요. 버그를 잡는 일입니다. 다른 하나는 확인(validation), ‘그 모형이 현실을 충분히 닮았는가?’예요. 모형의 가정이 맞는지 따지는 일입니다.

검증에는 몇 가지 단골 방법이 있습니다. 답을 아는 경우와 맞춰 보기(M/M/1 공식), 서로 다른 방식으로 잰 값이 앞뒤가 맞는지 보기(리틀의 법칙, 이용률 = λ/μ), 극단적인 입력에서 상식대로 움직이는지 보기(도착이 0이면 대기도 0), 그리고 반복끼리 결과가 적당히 달라지는지 보기(시드 버그)예요.

확인은 현실 데이터와 비교합니다. 모형을 맞추는 데 쓴 데이터와 다른 데이터로 비교해야 의미가 있어요(최적화 101의 보정과 같은 원칙). 로봇 시뮬레이터에서 학습한 정책이 실제 로봇에서 안 되는 sim-to-real 문제가 바로 ‘확인이 부족한 모형’의 대가입니다.

한 줄로검증은 ‘코드가 모형대로인가’, 확인은 ‘모형이 현실을 닮았나’입니다. 이론값과의 비교, 리틀의 법칙 같은 내부 일관성, 극단값 시험, 반복 간 변동으로 버그를 잡아요.

확인(validation)
모형이 목적에 맞게 현실을 닮았는지 확인.
내부 일관성
다른 방식으로 잰 값끼리 이론적 관계가 맞는가.

조금 더 정확하게

검증의 핵심은 ‘이미 아는 것’과의 비교입니다. 단순화한 경우(지수분포, 서버 하나)의 해석해, 보존 관계(들어온 수 = 나간 수 + 안에 남은 수), 내부 일관성(시간 평균 Lq와 λ̂·평균 Wq), 대칭과 단조성(처리가 빨라지면 대기가 줄어야 함)을 점검표로 만들어 코드를 바꿀 때마다 자동으로 돌려요. 신뢰구간이 이론값을 품는지로 판단하면 우연한 흔들림과 버그를 가를 수 있습니다.

확인은 끝이 없는 일이라 목적이 범위를 정합니다. ‘하루 평균 대기’가 목적이면 그 값을 현장 기록과 비교하고, 얼굴 타당성(현장 사람이 보기에 그럴듯한가), 입력 가정을 바꿨을 때 결론이 바뀌는지(민감도), 과거 데이터를 재현하는지를 봐요. 보정에 쓴 데이터와 확인에 쓴 데이터를 나누는 것이 가장 중요한 습관입니다.

실습에는 실제로 흔한 버그 세 개를 심어 두었습니다. 대기 시간에 충전 시간까지 더하는 버그, 처리율 자리에 평균 시간을 넣는 단위 버그, 반복마다 같은 시드를 쓰는 버그예요. 어떤 점검이 어떤 버그를 잡는지가 점검표를 여러 개 두는 이유를 보여 줍니다.

검증의 기준들
(9)
  1. 1이용률 점검. 충전기가 바쁜 비율이 λ/μ와 맞아야 해요.
  2. 2리틀의 법칙 점검. 시간 평균으로 잰 줄 길이와 관측 평균 대기 × 도착률이 맞아야 합니다.
  3. 3이론값 점검. 반복의 신뢰구간이 이론값을 품어야 해요. 품지 못하면 버그나 워밍업을 의심합니다.
파이썬
import numpy as np

def check(sim, lam=1/10, mu=1/8, R=10):
    res = [sim(np.random.default_rng(s)) for s in range(R)]        # (util, Lq, lam_hat, Wq)
    util, Lq, lam_hat, Wq = map(np.array, zip(*res))
    rho = lam / mu; Wq_th = rho / (mu - lam)
    h = 2.26 * Wq.std(ddof=1) / np.sqrt(R)
    return {
        '이용률 = λ/μ':     abs(util.mean() - rho) < 0.03,
        '리틀 Lq = λWq':    abs(Lq.mean() - (lam_hat * Wq).mean()) < 0.1 * Lq.mean(),
        '이론값이 구간 안':  abs(Wq.mean() - Wq_th) <= h,
        '반복 간 변동 > 0':  Wq.std() > 0,
    }
# 버그가 있는 시뮬레이터를 넣으면 어느 점검이 실패하는지 보인다

해 볼 것

  • 버그를 모두 끄고 [점검]을 누르세요. 네 점검이 모두 통과(초록)합니다. 그다음 [대기에 충전 시간 포함]을 켜면 리틀의 법칙 점검과 이론값 점검이 실패해요. 이용률 점검은 통과합니다.
  • [처리율 자리에 평균]을 켜면 충전이 1/8분 만에 끝나 이용률이 거의 0이 됩니다. 이용률 점검이 바로 잡아내요. 단위 버그는 이렇게 극단적인 결과를 내서 오히려 찾기 쉽습니다.
  • [반복마다 같은 시드]를 켜면 반복 10번이 모두 같은 결과라 신뢰구간의 폭이 0이 됩니다. 이론값 점검도 폭 0인 구간 때문에 실패하지만, 원인을 정확히 짚는 건 반복 간 변동 점검이에요. 이용률과 리틀의 법칙은 통과해서, 그 둘만 봤다면 놓쳤을 버그입니다.

핵심

검증은 이론값, 내부 일관성(리틀의 법칙), 극단값, 반복 간 변동 같은 점검표로 코드의 버그를 잡고, 확인은 보정에 쓰지 않은 현실 데이터와 비교해 모형의 가정을 따집니다. 점검은 여러 개를 함께 두세요.

먼저, 수식 없이

궤도에 위성 여덟 기가 떠서 함께 데이터센터 역할을 합니다. 위성은 방사선 때문에 가끔 고장 나고(평균 20일에 한 번), 고장 난 위성은 수리 로봇이 가서 고쳐요(평균 2일). 수리 로봇이 한 대뿐이면 동시에 여러 기가 고장 날 때 줄을 서야 합니다. 몇 %의 시간 동안 위성이 살아 있을까요? 수리 로봇을 두 대로 늘리면 얼마나 나아질까요?

이건 1~9단계를 모두 쓰는 문제입니다. 위성 여덟 기가 ‘손님’, 수리 로봇이 ‘서버’인 대기행렬이고, 사건은 ‘고장’과 ‘수리 끝’ 두 가지예요. 손님 수가 여덟로 정해져 있어서, 고장 난 위성이 많을수록 새로 고장 날 위성이 줄어드는 점만 M/M/1과 다릅니다.

이 단순한 경우에는 마르코프 연쇄로 정확한 답을 구할 수 있어서, 시뮬레이터를 검증한 뒤(9단계) 모형을 더 현실적으로 바꿔 나갈 수 있어요. 수리 시간이 지수분포가 아니거나, 수리 로봇이 위성 사이를 이동하는 시간이 있거나, 고장률이 태양 활동에 따라 바뀌는 경우는 식이 없으니 시뮬레이션만이 답입니다.

한 줄로고장·수리 시스템은 손님 수가 정해진 대기행렬입니다. 해석해로 시뮬레이터를 검증한 뒤, 반복과 신뢰구간으로 수리 로봇 수 같은 설계를 비교해요.

조금 더 정확하게

위성 한 기만 보면 가용도는 A = MTBF/(MTBF + MTTR) = 20/22 ≈ 91%입니다. 그런데 여덟 기가 수리 로봇 한 대를 나눠 쓰면 수리 대기가 생겨 그보다 낮아져요. 고장 난 위성 수 n을 상태로 두면 n에서 n + 1로는 (N − n)λ, n에서 n − 1로는 min(n, c)μ의 비율로 옮겨 가고, 정상 분포는 pn ∝ N!/(N − n)! × Π λ/(min(j, c)μ)입니다. 평균 고장 수로 가용도 A = 1 − (1/N)Σn·pn을 구해요.

시뮬레이터는 위성마다 ‘다음 고장 시각’을 사건 목록에 넣고, 고장이 꺼내지면 수리 로봇이 비었으면 ‘수리 끝’을 예약하고 아니면 줄에 세웁니다. 수리 끝이 꺼내지면 그 위성의 다음 고장을 예약하고 줄의 다음 위성 수리를 시작해요. 3단계의 충전기 시뮬레이터와 사건 종류 이름만 다릅니다.

수리 로봇 1대와 2대를 비교할 때는 8단계의 공통 난수로 같은 고장 이력을 넣고, 6단계의 반복과 신뢰구간으로 차이를 말합니다. 비용(로봇 한 대를 더 쏘아 올리는 값)과 가용도 향상을 함께 놓고 결정하는 것이 M&S의 마지막 단계예요.

고장과 수리: 가용도
(10)
  1. 1한 기의 가용도. 고장 사이 평균 시간 ÷ (그것 + 평균 수리 시간).
  2. 2고장 수의 정상 분포. 살아 있는 위성이 많을수록 고장이 잦고, 수리는 로봇 수만큼 동시에 돼요.
  3. 3군집의 가용도. 평균 고장 수를 N으로 나눠 1에서 뺍니다. 시뮬레이터를 검증하는 기준값이에요.
파이썬
import heapq, numpy as np

def constellation(N=8, c=1, mtbf=20.0, mttr=2.0, T=5000.0, seed=0):
    rng = np.random.default_rng(seed)
    Q = [(rng.exponential(mtbf), i, 'fail') for i in range(N)]; heapq.heapify(Q)
    broken, busy, line, last, area = 0, 0, [], 0.0, 0.0
    while Q:
        t, i, kind = heapq.heappop(Q)
        if t > T: break
        area += broken * (t - last); last = t
        if kind == 'fail':
            broken += 1
            if busy < c: busy += 1; heapq.heappush(Q, (t + rng.exponential(mttr), i, 'fix'))
            else: line.append(i)
        else:
            broken -= 1; heapq.heappush(Q, (t + rng.exponential(mtbf), i, 'fail'))
            if line: heapq.heappush(Q, (t + rng.exponential(mttr), line.pop(0), 'fix'))
            else: busy -= 1
    return 1 - area / last / N

for c in [1, 2]:
    A = [constellation(c=c, seed=s) for s in range(20)]
    print(c, np.mean(A).round(4), (2.09 * np.std(A, ddof=1) / np.sqrt(20)).round(4))
# 이론: 1대 0.8271, 2대 0.9018

핵심

고장과 수리는 손님 수가 정해진 대기행렬로 모형화하고, 해석해로 시뮬레이터를 검증한 뒤, 반복과 신뢰구간으로 수리 로봇 수 같은 설계를 비교합니다. 식이 없는 현실적인 변형은 같은 시뮬레이터를 고쳐서 풀어요.
