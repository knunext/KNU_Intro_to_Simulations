A2수강신청 서버: 10시 정각의 폭주

10시 정각, 수강신청이 열리자마자 1만 명이 거의 동시에 접속합니다. 서버는 하루 평균으로 보면 한가한데, 첫 몇 초는 처리 능력의 몇 배가 몰립니다. 기다리다 지친 학생들이 새로고침을 누르면 요청은 더 늘어납니다. 이 되먹임이 서버를 어떻게 무너뜨리는지, 서버를 늘리지 않고도 막을 방법이 있는지 사건 기반 시뮬레이션으로 확인합니다.

이 사례에서 해 볼 것

  • 평균 도착률로 한 용량 계획이 순간적인 몰림 앞에서 왜 틀리는지 1편의 공식으로 따져 봅니다.
  • 시간 초과와 재시도가 만드는 되먹임을 사건 기반 모델로 적고, 서버가 한번 무너지면 몰림이 지나가도 회복하지 못하는 현상을 재현합니다.
  • 작업자 수에 따라 결과가 갑자기 뒤집히는 절벽을 찾습니다.
  • 증설, 재시도 방식, 대기열 길이, 가상 대기실을 같은 조건에서 비교해 가장 싸고 확실한 대책을 고릅니다.
  • 5절에서 학생 에이전트 1,000명을 보며 서버를 직접 늘리고, 대책을 켜고, 공지를 내 봅니다.

1질문과 개념 모델

서버만 모델링하면 답이 틀립니다. 기다리다 새로고침을 누르는 사람까지 모델 안에 넣어야 합니다.

1.1질문 정하기단계 1

학생 1만 명이 10시 정각에 수강신청을 시작합니다. 신청 서버에는 요청을 처리하는 작업자(스레드)가 16개 있고, 요청 하나를 처리하는 데 평균 0.05초가 걸립니다. 질문은 셋입니다. 이 서버로 버틸 수 있는가? 버티지 못한다면 작업자를 몇 개까지 늘려야 하는가? 늘리지 않고 설계를 바꿔서 해결할 수는 없는가?

1.2개념 모델단계 2

학생
75%는 10시 직후 몇 초 안에(평균 3초), 나머지는 조금 늦게(평균 20초) 첫 요청을 보냅니다. 학생 한 명은 성공 한 번이면 끝납니다.
서버
작업자 c개가 대기열 하나에서 요청을 꺼내 처리합니다. 처리 시간은 평균 0.05초인 지수분포입니다. 작업자 16개의 처리 능력은 초당 320건입니다.
대기열 상한
대기열에 K개가 차 있으면 새 요청은 바로 거절됩니다("잠시 후 다시 시도하세요" 화면). 1편의 M/M/c/K와 같은 구조입니다.
시간 초과
10초 안에 처리가 시작되지 않으면 학생의 브라우저는 포기하고, 학생은 새로고침을 누릅니다. 그런데 서버는 그 사실을 모르고, 대기열에 남은 그 요청을 나중에 처리합니다. 받을 사람이 없는 헛일입니다.
재시도
거절이나 시간 초과를 겪은 학생은 0.5~1.5초 뒤에 다시 요청합니다(즉시 새로고침). 대책으로 쓰는 다른 방식은 3.2절에서 다룹니다.

실제 수강신청은 로그인, 과목 검색, 신청을 여러 번 오가고, 데이터베이스의 잠금 경쟁도 있습니다. 여기서는 그것을 "요청 한 번"으로 줄였습니다. 질문이 "되먹임이 서버를 무너뜨리는가"이기 때문에, 그 되먹임을 만드는 시간 초과와 재시도는 반드시 남겼습니다.

2데이터와 구현

평균으로 보면 아무 문제가 없어 보입니다. 그것이 문제입니다.

2.1데이터 모으기단계 3

지난 학기의 서버 접속 기록이 가장 좋은 자료입니다. 요청마다 도착 시각, 처리 시작과 끝 시각, 응답 코드, 세션 번호가 남아 있으면 첫 요청이 몰리는 모양(4편의 시간에 따라 변하는 도착), 처리 시간의 분포, 같은 학생이 몇 초 간격으로 다시 요청하는지까지 알 수 있습니다.

1편의 공식으로 먼저 어림해 봅시다. 4분 동안 1만 명이면 평균 도착률은 초당 42건이고, 처리 능력 320건에 대한 이용률은 ρ = 0.13입니다. 평균으로는 서버가 87% 놀고 있습니다. 하지만 첫 5초에는 7천 명 가까이가 몰려 초당 1,400건 안팎이 들어옵니다. 이때 ρ는 4를 넘고, 대기열은 초당 천 건 넘게 늘어납니다. 정상 상태를 가정하는 공식은 이 몇 초를 다루지 못합니다.

2.2프로그램 짜기단계 4

사건은 다섯 가지입니다. 요청 도착, 처리 끝, 시간 초과, 재시도, 그리고 가상 대기실을 쓸 때의 입장. 2편의 미래 사건 목록 하나로 모두 돌아갑니다. 아래 그래프의 세로축은 로그 눈금입니다.

10시 정각부터 4분

회색은 초마다 들어온 요청(재시도 포함), 색 선은 학생에게 실제로 전달된 응답, 빨간 선은 시간 초과입니다. 가로 점선이 서버의 처리 능력입니다.

재시도
대기열 상한

기본 설정에서는 처음 몇 초 뒤 시간 초과(빨강)가 쏟아지고, 들어오는 요청(회색)이 처리 능력의 열 배 가까이로 치솟은 채 내려오지 않습니다. 몰림이 끝난 뒤에도 서버는 계속 바쁘지만 학생에게 전달되는 응답(색 선)은 거의 없습니다. 바쁜데 아무 일도 못 하는 상태입니다.

2.3검증과 타당성단계 5

검증. 시간 초과를 없애고 대기열을 무제한으로 두면 이 모델은 1만 건을 한꺼번에 받은 M/M/16 서버가 됩니다. 그러면 마지막 요청은 대략 10,000/320 ≈ 31초에 끝나야 합니다. 작업자를 24개로 둔 설정에서 무너지지 않는 것도 같은 계산(10,000/480 ≈ 21초, 대부분의 요청이 10초 전에 처리 시작)과 맞습니다. 서버 상자에 대해 처리량 × 평균 체류시간 = 평균 요청 수(리틀의 법칙)도 확인합니다.

타당성. 실제 접속 기록에서 몰림이 시작된 뒤 몇 초 만에 오류가 늘기 시작했는지, 오류 비율이 몰림이 지나간 뒤에도 높게 남았는지를 비교합니다. "몰림이 끝나도 회복하지 않는다"는 패턴이 기록에 있다면 이 모델의 핵심 가정, 곧 헛일과 재시도의 되먹임이 실제로 일어난다는 증거입니다.

3실험과 결정

작업자를 하나씩 늘려 보고, 같은 작업자로 설계만 바꿔 봅니다.

3.1작업자 수의 절벽단계 6

작업자 수와 60초 안에 성공한 학생 비율

작업자 수마다 같은 시드로 4분을 돌렸습니다. 세 설계를 비교합니다.

즉시 새로고침에 대기열을 무제한으로 두면 작업자 18개까지는 절반도 성공하지 못하다가, 20개에서 갑자기 모두 성공합니다. 처리 능력이 360건에서 400건으로 11% 늘었을 뿐인데 결과가 뒤집힙니다. 문턱은 시간 초과 10초 동안 처리할 수 있는 양, 곧 대기열 길이 10초 × 처리 능력입니다. 대기열이 이보다 길어지면 뒤쪽 요청은 처리가 시작되기 전에 모두 시간 초과가 되고, 서버는 그 죽은 요청들을 처리하느라 산 요청을 처리하지 못합니다. 그러면 재시도가 다시 대기열을 채웁니다. 몰림이 지나가도 이 상태가 스스로 유지되는 것을 준안정 고장(metastable failure)이라 부릅니다.

3.2대책 비교단계 6

작업자 16개를 그대로 두고 설계를 바꿔 봅니다. 시드 5개로 돌린 평균입니다. 요청 배수는 학생 한 명이 보낸 요청의 평균 개수이고, 헛일은 서버가 처리했지만 학생에게 전달되지 않은 처리의 비율입니다.

3.3분석과 결정단계 7

지수 백오프는 요청 수를 셋째로 줄였지만 결과는 그대로입니다. 문제가 재시도의 양이 아니라 헛일이기 때문입니다. 반대로 서버가 처리를 시작하기 전에 "이 요청은 이미 10초가 지났다"를 확인해 버리기만 해도, 또는 대기열을 짧게 잘라 오래 기다릴 요청을 처음부터 거절하기만 해도 같은 서버로 모두가 성공합니다. 거절은 처리보다 훨씬 싸기 때문에, 요청이 여덟 배로 늘어도 서버는 버팁니다.

가상 대기실은 학생을 서버 앞이 아니라 번호표 줄에 세웁니다. 서버에는 처리할 수 있는 만큼만 들여보내므로 재시도도 헛일도 없고, 먼저 온 학생이 먼저 들어가는 공정함도 지켜집니다. 첫 응답까지의 중앙값은 대기실이 11초 남짓으로 만료 요청 버리기(9.5초)보다 조금 길지만, 늦게 성공하는 학생 쪽(95번째 백분위)은 대기실이 17초 남짓으로 더 짧습니다. 수강신청과 공연 예매 사이트가 대기 순번을 보여 주는 이유입니다.

결정: 작업자를 늘리는 것도 답이지만, 절벽 바로 위에 서는 증설은 위험합니다. 학생이 조금만 늘거나 처리가 조금만 느려져도 다시 떨어집니다. 이 모델로는 만료된 요청 버리기를 먼저 넣고, 가상 대기실을 두는 것이 가장 싸고 확실합니다. 두 대책은 서로를 대신하지 않으므로 함께 쓰는 것이 보통입니다.

4연결과 정리

4.1모델의 한계

요청 한 번
실제로는 학생 한 명이 여러 과목을 신청하고, 인기 과목에는 데이터베이스 잠금 경쟁이 생깁니다. 병목이 서버가 아니라 데이터베이스일 수도 있습니다.
같은 학생
모두 똑같이 10초를 기다리고 똑같이 새로고침합니다. 실제로는 더 빨리 포기하는 사람, 탭을 여러 개 여는 사람이 있습니다(3편의 개체 차이).
지수분포 처리 시간
처리 시간의 꼬리가 더 길면 문턱이 더 낮아집니다(1편 2.6절의 세 손잡이).
절벽의 위치
문턱 근처(작업자 18~20개)에서는 시드에 따라 무너지기도 하고 버티기도 합니다. 그 확률을 재는 것은 5-2편의 희귀 사건 문제입니다(연습 4).

4.2쓰인 편들

1편평균 이용률 0.13은 리틀의 법칙과 M/M/c로 계산한 값이고, 대기열 상한은 M/M/c/K입니다. 공식이 몰림의 몇 초를 다루지 못한다는 것도 1편의 정상 상태 가정에서 나옵니다.

2편도착, 처리 끝, 시간 초과, 재시도는 모두 미래 사건 목록 하나로 돌아갑니다.

5편과 5-2편대책 비교는 같은 시드로 했고(공통 난수), 문턱 근처에서 무너질 확률은 희귀 사건 기법으로 잽니다.

8편시간 초과를 없앤 특수한 경우를 손계산과 비교한 것이 검증입니다.

4.3파이썬으로 확인하기

같은 모델을 표준 라이브러리만으로 짰습니다. 3.2절 표의 대책을 차례로 돌립니다(시드 1).

# registration.py : 수강신청 오픈 순간의 서버. 시간 초과와 재시도가 서버를 무너뜨리는 과정
import heapq, itertools, random

def run(c=16, K=50_000, policy="now", drop_expired=False, N=10_000, svc=0.05, tout=10.0, T=240.0, seed=1):
    rng, tick = random.Random(seed), itertools.count()
    ev = []                                       # (시각, 순번, 종류, 자료)
    def push(t, kind, data): heapq.heappush(ev, (t, next(tick), kind, data))
    first, done, tries = [0.0] * N, [None] * N, [0] * N
    for s in range(N):                            # 75%는 오픈 직후, 25%는 조금 늦게
        first[s] = max(rng.random() * 0.5, -1 + rng.expovariate(1 / 4)) if rng.random() < 0.75 else rng.expovariate(1 / 20)
        push(first[s], "enter" if policy == "room" else "send", s)
    if policy == "room":
        room, rate = [], c / svc * 0.95           # 가상 대기실: 처리 능력의 95%로만 들여보낸다
        push(0.0, "admit", None)
    queue, busy, requests, work, wasted = [], 0, 0, 0.0, 0.0
    def retry(s, t):
        tries[s] += 1
        delay = rng.uniform(0, min(30, 0.5 * 2 ** min(tries[s], 10))) if policy == "backoff" else rng.uniform(0.5, 1.5)
        push(t + delay, "send", s)
    def start(t):
        nonlocal busy, work
        while busy < c and queue:
            req = queue.pop(0)
            if req["dead"] and drop_expired:      # 이미 떠난 학생의 요청은 처리하지 않는다
                continue
            req["started"], busy = True, busy + 1
            d = rng.expovariate(1 / svc); work += d
            push(t + d, "done", (req, d))
    while ev:
        t, _, kind, x = heapq.heappop(ev)
        if t > T: break
        if kind == "enter": room.append(x)
        elif kind == "admit":
            if room: push(t, "send", room.pop(0))
            push(t + 1 / rate, "admit", None)
        elif kind == "send":
            requests += 1
            if len(queue) >= K: retry(x, t + 0.1); continue        # 대기열이 꽉 차면 바로 거절
            req = {"s": x, "dead": False, "started": False}
            queue.append(req)
            if policy != "room": push(t + tout, "timeout", req)
            start(t)
        elif kind == "timeout":
            if not x["started"]: x["dead"] = True; retry(x["s"], t)  # 학생은 기다리다 새로고침
        elif kind == "done":
            req, d = x; busy -= 1
            if req["dead"]: wasted += d                              # 아무도 받지 않는 응답
            elif done[req["s"]] is None: done[req["s"]] = t
            start(t)
    ok60 = sum(1 for s in range(N) if done[s] is not None and done[s] - first[s] <= 60) / N
    return ok60, requests / N, (wasted / work if work else 0.0)

cases = [("즉시 새로고침, 큰 대기열", {}), ("+ 만료된 요청 버리기", {"drop_expired": True}),
         ("지수 백오프", {"policy": "backoff"}), ("대기열을 2초분으로", {"K": 640}),
         ("가상 대기실", {"policy": "room"}), ("작업자 24개로 증설", {"c": 24})]
for name, kw in cases:
    ok, amp, waste = run(**kw)
    print(f"{name}: 60초 안에 성공 {ok:.0%}, 요청 {amp:.1f}배, 헛일 {waste:.0%}")
즉시 새로고침, 큰 대기열: 60초 안에 성공 36%, 요청 25.4배, 헛일 95%
+ 만료된 요청 버리기: 60초 안에 성공 100%, 요청 1.2배, 헛일 0%
지수 백오프: 60초 안에 성공 36%, 요청 8.1배, 헛일 95%
대기열을 2초분으로: 60초 안에 성공 100%, 요청 7.8배, 헛일 0%
가상 대기실: 60초 안에 성공 100%, 요청 1.0배, 헛일 0%
작업자 24개로 증설: 60초 안에 성공 100%, 요청 1.0배, 헛일 0%

4.4연습과 확장

1. 시간 초과를 10초에서 30초로 늘리면 무너지는 작업자 수의 문턱은 어떻게 될까요?

문턱이 되는 대기열 길이(시간 초과 × 처리 능력)가 세 배로 길어지므로 더 적은 작업자로도 버틸 가능성이 큽니다. 대신 학생 한 명이 기다리는 시간은 길어집니다. 시간 초과는 사용자 경험과 서버 안정성 사이의 손잡이입니다. 위젯 코드나 파이썬 코드의 tout를 바꿔 확인해 보세요.

2. 학생 한 명이 과목 세 개를 따로 신청해야 한다면 무엇을 바꿔야 할까요?

성공 횟수를 학생마다 세고, 세 번째 성공까지 걸린 시간을 재도록 바꿉니다. 요청이 세 배가 되므로 같은 작업자 수에서는 문턱 아래로 떨어지기 쉽습니다. 과목마다 정원이 있다면 "정원 마감"이라는 새 응답도 생기고, 마감된 과목을 보고 다른 과목으로 바꾸는 행동은 에이전트의 판단이 됩니다.

3. 가상 대기실의 입장 속도를 처리 능력의 110%로 올리면 어떻게 될까요?

들어오는 양이 처리 능력보다 많으므로 서버 앞에 다시 줄이 생기고, 그 줄이 10초분을 넘으면 기본 설정과 같은 붕괴가 일어날 수 있습니다. 대기실은 입장 속도를 처리 능력보다 낮게 둘 때만 안전합니다. 실제 시스템은 서버의 응답 시간을 보고 입장 속도를 자동으로 조절합니다(되먹임 제어).

4. 작업자 19개에서 이 서버가 무너질 확률을 재려면 어떻게 해야 할까요?

시드를 바꿔 수백 번 돌리고 "60초 안 성공 비율이 50% 아래"인 실행의 비율을 셉니다. 그 확률이 아주 작다면(작업자 22개처럼) 단순 반복으로는 한 번도 못 볼 수 있으므로, 5-2편의 스플리팅처럼 대기열이 길어진 상태를 복제해 이어 돌리는 방법을 씁니다.

5직접 돌려 보기: 학생 1,000명과 서버

이번에는 학생 한 명 한 명을 에이전트로 보면서, 10시 정각부터 4분 동안 서버 관리자가 되어 직접 개입해 봅니다.

화면에 담으려고 모델을 10분의 1로 줄였습니다. 학생 1,000명, 작업자 16개, 처리 시간 평균 0.5초라서 처리 능력은 초당 32건입니다. 학생 수에 대한 처리 능력의 비율은 3절과 같습니다. 대신 학생들을 조금 더 사람답게 만들었습니다. 기다릴 수 있는 시간이 사람마다 5~15초로 다르고, 10%는 탭을 세 개 열어 한 번에 요청을 세 개씩 보내며, "새로고침 자제" 공지가 나가면 절반만 따릅니다(3편의 개체 차이).

재생 중에 언제든 서버를 늘리고 줄이거나, 만료 요청 버리기와 지수 백오프를 켜고 끄거나, 공지를 낼 수 있습니다. 작업자 수, 탭 비율, 가상 대기실은 "처음부터"를 누를 때 적용됩니다.

5.1큐 네트워크로 보기

위 아래 그림은 같은 시뮬레이션을 두 방식으로 보여 줍니다. 위는 학생 한 명 한 명(에이전트), 아래는 1편 2.8절의 큐 네트워크입니다. 이 시스템에는 일반적인 큐에 없는 노드가 하나 있습니다. 시간 초과나 거절을 겪은 학생이 잠시 머물렀다 다시 들어오는 "새로고침 대기"입니다. 큐잉 이론에서는 이런 구조를 재시도 큐(retrial queue), 이 노드를 궤도(orbit)라고 부릅니다.

1편의 트래픽 방정식으로 읽어 봅시다. 대기열을 떠나는 요청 중 비율 r이 시간 초과로 되돌아온다면, 첫 요청의 흐름이 λ0일 때 대기열에 들어오는 전체 흐름은 λ0/(1 − r)입니다. 2.8절 잭슨 네트워크의 "다시 만듦"과 같은 식입니다. 무너진 상태에서는 r이 1에 가까워져, 첫 요청이 거의 끝난 뒤에도 재시도 화살표 하나가 대기열을 계속 채웁니다. 시간 초과와 재시도 화살표가 굵고 성공 화살표가 가늘어지는 순간이 위 그림의 화면이 빨갛게 덮이는 순간입니다.

아래 그림의 숫자 줄은 서버 대기열 노드에 리틀의 법칙을 적용한 것입니다. 무너진 뒤 대기열이 계속 길어지는 상태에서도 L과 λW가 거의 같게 나옵니다(시드 1, 120초 무렵 L ≈ 5,600, λW ≈ 5,670). 몰림이 막 시작된 첫 몇 초처럼 상태가 빠르게 바뀔 때는 10초 창 안에서 들어온 요청과 나간 요청이 달라 두 값이 어긋납니다. 리틀의 법칙은 오래 관측했을 때의 법칙이라는 것을 눈으로 볼 수 있습니다.

5.2해 볼 것

  1. 그냥 지켜보기10초쯤 지나면 왼쪽이 빨간 칸(오류, 새로고침)으로 덮이고, 오른쪽 작업자 상자가 회색(헛일)으로 바뀝니다. 대기열은 "10초분" 선을 넘어 계속 자랍니다. 이 설정으로 시드 세 개를 돌리면 60초 안에 성공한 학생은 평균 32%였습니다.
  2. 무너진 뒤에 증설하기20초쯤 "긴급 증설 +8"을 한 번 누르세요. 작업자가 24개가 되어도 회복하지 못합니다(시드 1에서 60초 안 성공 34%). 그런데 처음부터 작업자를 24개로 두면 75%가 성공합니다. 같은 서버라도 무너지기 전에 갖췄는지, 무너진 뒤에 갖췄는지에 따라 결과가 다릅니다. 무너진 뒤에는 대기열에 쌓인 죽은 요청까지 처리해야 하므로 훨씬 많이 늘려야 합니다.
  3. 무너진 뒤에 만료 요청 버리기처음부터 다시 돌려 무너지게 둔 뒤, 60초쯤 "만료 요청 버리기"를 켜세요. 작업자 상자가 다시 청록색으로 바뀌고 성공이 빠르게 늘어 4분 안에 모두 성공합니다. 증설보다 이쪽이 회복에 강한 이유는, 쌓인 헛일을 한꺼번에 치워 주기 때문입니다.
  4. 공지와 탭"새로고침 자제" 공지는 요청 수를 조금 줄일 뿐 무너진 상태를 되돌리지는 못합니다. 탭 여러 개 비율을 30%로 올리고 처음부터 돌리면 더 빨리, 더 깊게 무너집니다(시드 세 개 평균 60초 안 성공 23%). 한 사람의 영리한 행동이 모두에게 손해가 되는 예입니다.
  5. 가상 대기실"가상 대기실"을 고르고 처음부터 누르세요. 회색 칸(대기실)이 차례로 줄어들며 들어가고, 오류도 헛일도 없이 모두 성공합니다.
  6. 네트워크에서 고리 찾기아래 큐 네트워크 그림에서 시간 초과와 재시도 화살표가 만드는 고리를 보세요. 무너질 때는 이 고리의 흐름이 첫 요청의 흐름보다 커집니다. 만료 요청 버리기를 켜면 "만료 버림" 노드가 생겨 고리를 끊고, 가상 대기실을 쓰면 고리 자체가 사라집니다.

이 시뮬레이터의 숫자는 3.2절 표와 다릅니다. 학생 수를 줄이고 사람마다 다른 행동을 넣었기 때문입니다. 비교할 것은 숫자가 아니라 패턴입니다. 두 모델 모두에서 서버는 문턱을 넘으면 스스로 회복하지 못하고, 만료 요청 버리기와 가상 대기실은 같은 서버로 문제를 풉니다. 서로 다른 두 모델이 같은 패턴을 보이면 그 결론을 더 믿을 수 있습니다(8편).
