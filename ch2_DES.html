앞 편: 리틀의 법칙, 직접 돌려보기

프롬프트 커피점에서 배우는
이산사건 시뮬레이션

IT대학 앞 광장의 빨간 컨테이너 카페 하나를 모델로 만들어 봅니다. 점원 한 명이 아메리카노만 파는 단순한 가게에서 출발해 메뉴, 주문 개수, 인원, 키오스크, 기계, 붐비는 시간대, 손님의 선택을 한 단계에 하나씩 더해 갑니다. 단계마다 무엇이 공식으로 풀리고 무엇이 시뮬레이션으로만 풀리는지 직접 확인할 수 있습니다.

    수업 진행 예시 (3회)

    1. 1회차: 기초대기행렬 이름 읽기, 무작위 손님과 난수, DES 개념, 시뮬레이터 1~3단계, 직접 짜 보기
    2. 2회차: 여러 서버와 네트워크시뮬레이터 4~6단계, 큐 네트워크, 큐 구조와 DES
    3. 3회차: 하루 운영과 통계시뮬레이터 7~8단계, 반복 실행과 신뢰구간, 다음 단계

    심화 표시가 붙은 부분은 건너뛰어도 흐름을 따라가는 데 문제가 없습니다.

    먼저, 대기행렬 이름 읽는 법

    이 페이지에는 M/G/1, M/G/c 같은 이름이 자주 나옵니다. 켄달(Kendall) 표기법이라고 하며, 빗금으로 나눈 칸마다 대기행렬의 성질을 하나씩 적습니다. 네 번째 칸부터는 기본값(줄 길이 무제한, 선착순)이면 생략합니다.

    확률·통계를 잊었다면: 30초 복습

    이 페이지에 필요한 건 네 단어뿐입니다. 바리스타 두 명이 아메리카노를 다섯 잔씩 만든 시간으로 보겠습니다.

    평균
    다 더해서 개수로 나눈 값. 두 사람 모두 1.0분입니다.
    분산, 표준편차
    값들이 평균에서 얼마나 떨어져 있나. 차이를 제곱해서 평균 낸 것이 분산, 그 제곱근이 표준편차입니다. A는 0, B는 약 0.63분.
    변동계수 CV
    표준편차 ÷ 평균. 단위가 없어서 "평균에 비해 얼마나 들쭉날쭉한가"를 비교할 수 있습니다. A는 0, B는 0.63. 이 페이지의 C²는 이것의 제곱입니다(B는 0.40).
    분포
    어떤 값이 얼마나 자주 나오는지의 모양. "지수 분포", "감마 분포"는 그 모양의 이름입니다. 시뮬레이터는 매번 이 모양에 맞춰 무작위로 값을 뽑습니다.

    평균은 같아도 B 뒤에 선 손님이 더 오래 기다립니다. 이 페이지 내내 반복되는 이야기입니다.

    칸에 들어가는 기호

    M
    마르코프(Markov), 즉 기억이 없는 지수 분포. 도착 칸에서는 포아송 도착, 서비스 칸에서는 지수 분포 서비스 시간. 변동계수 C² = 1.
    D
    결정적(Deterministic). 간격이나 시간이 항상 같음. C² = 0.
    Ek
    얼랑(Erlang) 분포. 지수 단계 k개를 이어 붙인 것으로, M과 D 사이. C² = 1/k.
    G
    일반(General) 분포. 평균과 분산만 알면 됩니다. 도착 칸에서는 GI(서로 독립인 일반 간격)라고도 씁니다.
    Mt
    도착률이 시간에 따라 바뀌는 포아송 도착. 이 페이지의 7단계(시간대별)입니다.
    c, K
    같은 서버의 수, 시스템에 들어올 수 있는 최대 인원(줄 + 서비스 중). 생략하면 K = ∞.

    꼭 쓰는 양

    λ, μ
    도착률, 서버 한 대의 서비스율. μ = 1/E[S].
    ρ = λ / cμ
    가동률. 1보다 작아야 줄이 끝없이 늘지 않습니다. 1에 가까울수록 대기는 1/(1−ρ)에 비례해 폭증합니다.
    L, Lq, W, Wq
    시스템 안 평균 인원, 줄에 선 평균 인원, 평균 체류시간, 평균 줄 대기시간. W = Wq + 1/μ, L = λW, Lq = λWq.
    Ca², Cs²
    도착 간격과 서비스 시간의 변동계수 제곱(분산 ÷ 평균²). 평균이 같아도 이 값이 크면 더 오래 기다립니다.
    단위 주의
    이 페이지의 모든 계산은 분 단위입니다. 도착률은 말하기 편하게 "명/시간"으로 조절하지만, 공식에 넣을 때는 60으로 나눕니다. 36명/시간 = 0.6명/분. 그래야 ρ = λ × E[S]에서 단위가 맞습니다: 0.6명/분 × 1.4분 = 0.84.

    알아 둘 모델 여섯 개

    모델평균 줄 대기 Wq한 줄 요약이 페이지에서
    M/M/1ρ / μ(1−ρ)모든 것의 출발점. L = ρ/(1−ρ).앞 편 리틀의 법칙 페이지
    M/D/1ρ / 2μ(1−ρ)서비스 시간이 일정하면 대기가 M/M/1의 딱 절반.1단계에서 분포를 "고정"으로
    M/G/1λE[S²] / 2(1−ρ)폴라체크-힌친(P-K) 공식. 위 둘을 모두 포함하며, 평균과 분산만 있으면 됩니다.1~3단계 "이론값과 비교"
    M/M/cP대기 / (cμ − λ)P대기는 얼랑 C 공식으로 구하는, 도착한 손님이 기다려야 할 확률.여러 대 서버의 기준 모델
    M/G/c≈ (1+Cs²)/2 × M/M/c 값정확한 닫힌 식이 없고 근사식만 있습니다.키오스크 주문 줄, 에스프레소 대기열
    G/G/1≈ ρ/(1−ρ) × (Ca²+Cs²)/2 × E[S]킹맨(Kingman) 근사. 대기 = 혼잡도 × 변동 × 서비스 시간.네트워크 뒤쪽 노드 (도착이 포아송이 아님)

    복잡한 Wq를 말로 읽기

    위 표의 식들은 생김새가 달라 보이지만, 사실 거의 같은 모양입니다. 확률 공식을 몰라도 아래 세 개의 손잡이만 기억하면 됩니다. 모델을 고르면 그 모델의 원래 식, 숫자를 넣은 계산, 세 손잡이로 쪼갠 값이 함께 나옵니다. 모델마다 어떤 손잡이가 가정으로 고정되는지(회색), 그 가정이 대기를 얼마나 바꾸는지 아래 비교 그래프에서 확인해 보세요.

    혼잡도×변동×한 명 서비스 시간

    ρ / (1 − ρ)×(Ca² + Cs²) / 2×E[S]

    같은 조건에서 여섯 모델 비교

    혼잡도
    가게가 바쁜 시간과 한가한 시간의 비율입니다. ρ = 0.5면 1, 0.8이면 4, 0.9면 9, 0.95면 19. 밀린 손님은 가게가 한가한 짧은 틈(1 − ρ)에만 빠지기 때문에, 그 틈이 반으로 줄면 대기는 두 배보다 훨씬 더 늘어납니다. 가동률 90%에서 95%로 "5%만" 올렸는데 대기가 두 배가 되는 이유입니다.
    변동
    손님이 얼마나 몰려서 오는지(Ca²)와 서비스가 얼마나 들쭉날쭉한지(Cs²)의 평균입니다. 둘 다 0이면(정확히 일정한 간격, 일정한 시간) 대기가 0이고, 완전히 무작위인 지수 분포면 1입니다. 줄은 "평균적으로 바빠서"가 아니라 "가끔 몰리고 가끔 늘어져서" 생깁니다.
    서비스 시간
    단위를 바꾸는 역할입니다. 앞의 두 손잡이를 곱하면 "앞사람 몇 명분을 기다리나"가 나오고, 거기에 한 명당 걸리는 시간을 곱하면 분 단위의 대기가 됩니다.

    여섯 모델을 이 틀로 다시 보기

    모델손잡이 값그래서 표의 식이 되는 이유
    M/M/1도착, 서비스 모두 무작위: 변동 = (1 + 1)/2 = 1혼잡도 × 1 × (1/μ) = ρ / μ(1−ρ). 표의 식 그대로입니다.
    M/D/1서비스 변동 0: 변동 = (1 + 0)/2 = ½M/M/1에 ½을 곱한 것. 그래서 "딱 절반"입니다.
    M/G/1도착은 무작위: 변동 = (1 + Cs²)/2표의 λE[S²] / 2(1−ρ)를 정리하면 정확히 이 모양이 됩니다. 근사가 아니라 등호입니다.
    G/G/1둘 다 일반: 변동 = (Ca² + Cs²)/2세 손잡이 그 자체(킹맨 근사). 도착이 포아송이 아니면 정확하지 않고 근사가 됩니다.
    M/M/c혼잡도가 P대기 / c(1−ρ)로 바뀜서버가 여럿이면 모두 바쁠 때만 기다리고(P대기), 줄은 c배 빨리 빠집니다(÷ c). 서버 1대면 P대기 = ρ라서 M/M/1로 돌아갑니다.
    M/G/c위 혼잡도에 변동 (1 + Cs²)/2M/M/c 값에 변동 손잡이를 곱한 것. 여러 서버에서는 이 곱이 정확하지 않아 "≈"입니다.

    P-K 공식에는 왜 제곱 E[S²]이 있을까

    버스 정류장을 떠올려 보세요. 버스가 평균 10분 간격으로 오는데 간격이 들쭉날쭉하다면, 아무 때나 정류장에 간 사람은 짧은 간격보다 긴 간격에 걸릴 가능성이 높습니다. 긴 간격이 시간을 더 많이 차지하니까요. 그래서 평균 기다림이 5분보다 깁니다.

    카페도 같습니다. 서비스가 오래 걸리는 손님은 첫째, 그 자체로 오래 걸리고, 둘째, 새로 온 손님이 그 손님의 서비스 도중에 도착할 가능성도 그만큼 큽니다. "길이"가 두 번 곱해지니 제곱이 나옵니다. 평균이 같아도 가끔 아주 오래 걸리는 손님(4개 주문, 라떼 여러 잔)이 섞이면 대기가 크게 늘어나는 이유입니다.

    알아 둘 것

    가동률이 먼저
    ρ ≥ 1이면 어떤 공식도 의미가 없습니다. 줄은 시간에 비례해 계속 길어집니다.
    변동이 대기를 만든다
    M/G/1과 킹맨 근사 모두 (Ca² + Cs²)/2 항이 대기를 곱합니다. 평균을 줄이는 것만큼 들쭉날쭉함을 줄이는 것이 중요합니다.
    같은 서버면 줄은 하나
    M/G/c는 줄 하나에 서버 c대입니다. 서버마다 줄을 따로 세우면(마트 계산대) 놀고 있는 옆 서버를 쓰지 못해 평균 대기가 길어집니다. 이를 줄 하나로 묶는 효과를 풀링(pooling)이라 합니다.
    네트워크 뒤쪽 노드
    앞 노드에서 나온 흐름이 뒤 노드의 도착이 되므로, 뒤 노드의 도착은 일반적으로 포아송이 아닙니다(M/M/c의 출발만 예외로 포아송). 노드마다 M/G/c 공식을 따로 적용하면 틀릴 수 있는 이유이고, 시뮬레이션이 필요한 이유입니다.
    리틀의 법칙은 예외 없음
    L = λW는 분포, 서버 수, 순서 규칙과 상관없이 어디에 경계를 그어도 성립합니다. 공식이 없는 모델에서도 시뮬레이션 결과를 점검하는 도구가 됩니다.

    무작위 손님은 어떻게 생겼나

    "손님이 포아송 과정으로 도착한다"는 말은 이렇게 생각하면 됩니다. 학생 수천 명이 각자 따로 "커피 한잔할까?"를 정합니다. 서로 상의하지 않고, 한 사람이 갈 확률은 아주 작습니다. 이런 결정이 모이면 가게 입장에서는 어느 순간에나 손님이 올 가능성이 같고, 앞 손님이 언제 왔는지와 상관이 없습니다. 그 결과 손님 사이 간격은 짧은 것이 많고 가끔 긴 공백이 생기는데, 이 간격의 모양이 지수 분포입니다.

    아래에서 평균은 똑같이 맞춘 세 가지 도착을 비교해 보세요. 숫자는 10분마다 온 손님 수입니다.

    컴퓨터는 무작위 간격을 어떻게 뽑나

    프로그래밍 언어가 주는 난수 Math.random()이나 random.random()은 0과 1 사이에서 어느 값이나 똑같이 나옵니다(균등 분포). 이걸 지수 분포로 바꾸는 데는 한 줄이면 됩니다.

    간격 = -평균 * ln(1 - U)      # U는 0~1 균등 난수
import math, random
gap = -mean * math.log(1 - random.random())   # 파이썬. random.expovariate(1/mean)와 같음

    왜 이렇게 되는지는 이렇게 보면 됩니다. U가 0.5면 "딱 중간쯤", 0.9면 "상위 10% 안에 드는 긴 값"이라는 뜻으로 읽고, 지수 분포에서 그 순위에 해당하는 간격을 찾아 주는 함수가 −평균 × ln(1 − U)입니다. 이런 방법을 역변환법이라고 합니다. U 대부분은 짧은 간격으로, 1에 가까운 소수의 U만 긴 간격으로 바뀝니다.

    평균 1분짜리 지수 분포로 바꿉니다.

    컴퓨터 난수는 사실 정해진 수열입니다(의사난수). 그래서 시뮬레이터의 "난수 씨앗"이 같으면 결과가 똑같이 재현됩니다. 감마 분포 같은 다른 모양도 같은 원리를 조금 응용해서 뽑습니다.

    이산사건 시뮬레이션이란

    커피점의 상태는 연속적으로 변하지 않습니다. 줄에 선 사람 수, 일하고 있는 점원 수, 돌고 있는 오븐 같은 값은 손님이 도착하거나 음료가 완성되는 순간에만 바뀝니다. 이런 순간을 사건(event)이라고 합니다. 사건과 사건 사이에는 아무것도 바뀌지 않으니, 시계를 다음 사건 시각으로 곧장 건너뛰면 됩니다. 이산사건 시뮬레이션(Discrete-Event Simulation, DES)의 핵심은 이것이 전부입니다.

    위: 대부분의 검사는 헛걸음이고, Δt 안에서 두 사건이 겹치면 순서가 뭉개집니다. 아래: 사건이 있는 시각만 처리하므로 빠르고, 시각이 정확합니다.

    구성 요소

    상태 변수
    지금 이 순간의 시스템. 줄에 선 손님 목록, 각 점원이 하는 일, 머신마다 쓰이는 칸 수.
    사건
    상태를 바꾸는 순간. 도착, 주문 완료, 제조 완료, 오븐 배치 완료 등.
    시뮬레이션 시계
    현재 시각 t. 실제 시간과 무관하게 사건 시각으로 점프합니다.
    미래 사건 목록(FEL)
    앞으로 일어날 사건을 시각 순으로 담은 우선순위 큐(최소 힙). 항상 가장 이른 것을 꺼냅니다.
    통계 누적기
    대기시간 합계, 줄 길이의 시간 적분(넓이) 같은 값. 사건 사이 구간마다 더해 둡니다.
    난수 스트림
    도착 간격과 작업 시간을 뽑는 의사난수. 씨앗(seed)이 같으면 같은 결과가 재현됩니다.

    메인 루프

    아래 시뮬레이터의 엔진은 다음 루프를 그대로 돌립니다. 사건 처리(B 단계) 직후에 "지금 시작할 수 있는 일"을 모두 검사하는 단계(C 단계)가 따로 있다는 점이 중요합니다. 두 단계의 테두리 모양은 아래 사건 그래프와 같습니다.

    1. while FEL이 비어 있지 않고 종료 조건이 아니면:
    2. e ← FEL에서 가장 이른 사건 꺼내기최소 힙 pop
    3. 통계 누적: 마지막 시각 → e.t 구간의 넓이 더하기줄 길이 × 시간

    이 카페의 사건 그래프

    실선 상자는 예약 사건(B 사건)입니다. 언제 일어날지 미리 알 수 있어 FEL에 들어갑니다. 점선 상자는 조건부 사건(C 사건)입니다. "점원과 에스프레소 머신이 둘 다 비어 있으면" 같은 조건이 맞는 순간에 시작되므로 FEL에 넣을 수 없고, 매 사건 뒤에 검사합니다. 이렇게 나누는 방식을 3단계 접근법(three-phase approach)이라고 합니다.

    모델: 컨테이너 카페 하나

    시간은 모두 분 단위입니다(도착률만 읽기 쉽게 명/시간으로 조절). 시스템 경계는 광장의 주문 줄부터 픽업 창구까지입니다. 손님은 줄을 서서 주문하고, 주문한 품목을 모두 받으면 떠납니다. 숫자는 실제로 잰 값이 아니라 그럴듯하게 정한 값입니다. 실제 관측으로 바꾸는 방법은 마지막 절에 있습니다.

    개체와 자원

    손님
    포아송 과정으로 도착하고 1~4개를 주문합니다. 주문(계산) 시간은 평균 0.3 + 0.1 × 품목 수분입니다.
    품목
    주문이 끝나면 품목마다 하나씩 생겨 제조 대기열에 들어갑니다. 손님 하나가 품목 여럿으로 갈라지고(fork), 모두 끝나야 다시 합쳐집니다(join).
    점원
    1~5명. 업무 방식은 세 가지입니다. 한 손님씩 끝까지는 주문받은 점원이 그 손님 품목을 모두 만듭니다. 분업은 1명이 계산만, 나머지가 제조만 합니다. 유연 분업은 계산 담당이 줄이 비면 제조를 돕습니다.
    계산대
    창구가 하나뿐이라 한 번에 한 손님만 주문할 수 있습니다.
    키오스크
    5단계부터 켜집니다. 손님이 직접 주문·결제하며 평균 0.5 + 0.15 × 품목 수분이 걸립니다. 켜면 점원은 모두 제조만 합니다.
    머신
    6단계부터 켜집니다. 에스프레소 머신(그룹 2개), 블렌더 1대, 핫도그 오븐(한 번에 4개까지 배치 조리).

    간략화한 가정

    재료는 떨어지지 않고 결제 실패도 없습니다. 오븐에 넣고 꺼내는 시간은 0으로 봅니다. 점원은 하던 일을 끝내기 전에 다른 일로 옮기지 않습니다(비선점). 5단계까지는 자원이 점원뿐이라 제조 대기열이 하나이고, 품목이 생긴 순서(FIFO)로 만듭니다. 6단계부터는 품목이 필요한 머신별 대기열(에스프레소, 블렌더, 머신이 필요 없는 점원만)에 따로 줄을 서고, 손이 빈 점원은 머신이 비어 있는 대기열들의 맨 앞 품목 가운데 가장 먼저 생긴 것을 집습니다. 완성된 품목은 바로 손님에게 건네집니다.

      사건 처리 기록

        초록색 줄은 그 사건 직후 C 단계에서 시작된 조건부 사건입니다.

        큐 구조가 DES 안에서 사는 방식 심화

        교과서의 대기행렬 모델은 부품처럼 생각할 수 있습니다. 하나의 대기열과 서버(M/G/1), 서버 여럿(M/G/c), 여러 큐를 이은 네트워크. 위 큐 네트워크 그림의 노드 하나하나가 이런 부품이고, DES 엔진 안에서는 모두 상태 변수 몇 개와 사건 규칙으로 바뀝니다. 서비스 시작은 조건이 맞아야 일어나는 C 사건, 서비스 종료는 FEL에 예약되는 B 사건, 어디로 보낼지(라우팅)는 B 사건 처리 코드 한 줄입니다.

        큐 구조카페에서엔진의 상태 변수엔진의 사건 규칙
        단일 서버 FIFO (M/G/1)점원 한 명이 받는 계산대대기 목록 cq, 사용 중 창구 수창구가 비면 맨 앞 손님 주문 시작(C), 주문 완료(B)에서 창구 반납

        포기 (balking)붐비면 돌아가는 손님손님별 허용 인원도착(B)에서 가게 앞 인원과 비교해 버리거나 줄에 넣기
        비정상 도착 (Mt)시간대별 도착률도착률 표 λ(t)다음 도착을 예약할 때 시간에 맞는 도착률 적용(thinning)

        머신별 대기열은 "하나의 공유 대기열에서 머신이 막힌 품목은 건너뛰고 가장 앞의 품목을 집는다"는 규칙과 고르는 순서가 똑같습니다. 같은 대기열 안의 품목은 필요한 머신이 같아서 함께 막히고 함께 풀리기 때문입니다. 실제로 두 방식으로 짠 엔진을 같은 씨앗으로 돌리면 결과가 소수점까지 같습니다. 그래도 대기열을 나눠 그려야 품목이 어느 머신 앞에서 기다리는지, 병목이 어디인지가 보입니다.

        심화 잭슨 네트워크: 공식이 어디까지 통하나

        모든 노드가 M/M/c이고 경로가 확률적으로만 갈라지는 네트워크라면 잭슨 네트워크라는 이름으로 각 노드를 따로 풀어 곱하면 정확한 답이 나옵니다. 하지만 이 카페에는 fork-join, 노드들이 함께 쓰는 점원, 배치 서버, 포기가 모두 들어 있어 그 가정이 깨집니다. 수식은 여기서 멈추지만, DES에게는 표의 한 줄씩이 조금 다른 규칙일 뿐입니다. 큐 이론은 각 부품의 성질을 알려 주고, DES는 그 부품들을 원하는 대로 조립해 돌려 볼 수 있게 해 줍니다.

        한 번 돌려서는 모른다

        시뮬레이션 결과는 난수에서 나온 표본 하나입니다. 씨앗을 바꿔 다시 돌리면 평균 체류시간이 꽤 달라집니다. 주사위를 한 번 던져서 "이 주사위는 4가 나온다"고 말할 수 없는 것과 같습니다. 그래서 같은 설정을 씨앗만 바꿔 여러 번(반복, replication) 돌리고, 반복마다 나온 결과들을 모아 판단합니다.

        모은 결과로 신뢰구간을 만듭니다. "진짜 장기 평균은 대략 이 범위 안에 있다"는 범위입니다. 만드는 방법은 세 단계입니다.

        ① 평균
        반복 결과들의 평균 x̄. 가운데 값입니다.
        ② 퍼짐 ÷ √n
        반복 결과들이 서로 얼마나 다른지(표준편차 s)를 √n으로 나눕니다. 반복을 4배 늘리면 이 값이 절반이 됩니다. 많이 모을수록 평균이 덜 흔들린다는 뜻입니다.
        ③ 안전 계수
        ②에 약 2를 곱해 앞뒤로 벌립니다. 정확히는 t값이라 부르는데, 반복이 적을수록 조금 크게 잡는 여유분입니다(20회면 2.09, 아주 많으면 1.96).

        x̄ ± t × s / √n

        "95% 신뢰구간"은 이렇게 만든 구간이 100번 중 95번쯤은 진짜 장기 평균을 품는다는 뜻입니다. 두 설정을 비교할 때 두 구간이 겹치지 않으면 "차이가 있다"고 말할 근거가 생깁니다.

        두 종류의 시뮬레이션을 구분해야 합니다. 1~6단계는 정상상태 시뮬레이션입니다. 가게가 끝없이 같은 조건으로 돌아갈 때의 장기 평균을 구하므로, 빈 가게에서 시작한 초반 구간(워밍업)은 버립니다. 7·8단계는 종료형 시뮬레이션입니다. 08시에 빈 가게로 열고 18시에 닫는 것 자체가 현실이므로 워밍업이 없고, "하루"가 반복 단위가 됩니다.

        두 설정을 비교할 때는 같은 씨앗 목록을 쓰면(공통 난수, common random numbers) 손님 도착이 똑같이 재현되어 차이만 또렷하게 보입니다. 아래 반복 실행은 현재 씨앗부터 차례로 씨앗을 바꿔 가며 돌리므로, 설정만 바꿔서 다시 누르면 공통 난수 비교가 됩니다.

        반복이 늘수록 좁아지는 신뢰구간

        반복을 하나씩 더할 때마다 평균(선)과 95% 신뢰구간(띠)이 어떻게 바뀌는지 보여 줍니다. 점은 각 반복의 결과입니다. 처음 몇 번은 띠가 넓고 출렁이다가, 반복이 쌓일수록 1/√n 비율로 좁아집니다.

        직접 짜 보기

        시뮬레이터가 어떻게 돌아가는지 가장 잘 아는 방법은 직접 짜 보는 것입니다. 자료구조 시간에 배운 힙(우선순위 큐) 하나면 FEL이 됩니다. 아래는 1단계 카페(점원 1명, 아메리카노만)를 파이썬 표준 라이브러리 heapq만으로 짠 코드입니다. 앞에서 본 메인 루프의 ①~⑤가 주석에 그대로 표시되어 있습니다. 실행하면 P-K 이론값(줄 대기 2.6분, 체류 4.0분)에 가까운 값이 나옵니다.

        import heapq, math, random

# ── 1단계 카페: 점원 1명, 아메리카노만 (시간 단위: 분) ──────────────
LAM = 30 / 60          # 도착률: 시간당 30명 = 분당 0.5명
ORDER_MEAN = 0.4       # 주문 받기 평균 0.4분 (= 0.3 + 0.1 × 1잔)
MAKE_MEAN = 1.0        # 아메리카노 만들기 평균 1.0분
END = 300_000          # 시뮬레이션 길이 (분). 길수록 이론값에 가까워짐

def expo(mean):
    """지수 분포 난수: 역변환법 한 줄 (= random.expovariate(1/mean))."""
    return -mean * math.log(1 - random.random())

random.seed(1)
fel = []                                   # 미래 사건 목록 (최소 힙)
def schedule(t, kind, who=None):
    heapq.heappush(fel, (t, kind, who))    # 시각이 가장 이른 사건이 맨 앞

# ── 상태 변수 ──
queue = []          # 줄 서 있는 손님의 도착 시각들
busy = False        # 점원이 일하는 중인가
# ── 통계 누적기 ──
area_q = 0.0        # 줄 길이 × 시간 (넓이) → 나누면 평균 줄 길이 Lq
last_t = 0.0
waits, stays = [], []

def start_service(t, arrive_time):
    """점원이 손님 한 명을 받는다 (C 사건: 점원이 비어 있을 때만)."""
    global busy
    busy = True
    waits.append(t - arrive_time)                      # 줄에서 기다린 시간
    schedule(t + expo(ORDER_MEAN), 'order_done', arrive_time)

schedule(expo(1 / LAM), 'arrive')          # 첫 손님 도착 예약
while fel:
    t, kind, who = heapq.heappop(fel)      # ① 가장 이른 사건 꺼내기
    if t > END:
        break
    area_q += len(queue) * (t - last_t)    # ② 통계 누적: 직전 사건부터 지금까지의 넓이
    last_t = t                             # ③ 시계를 사건 시각으로 점프

    if kind == 'arrive':                   # ④ B 사건 처리
        schedule(t + expo(1 / LAM), 'arrive')     # 다음 손님 도착 예약
        if busy:
            queue.append(t)                # 점원이 바쁘면 줄 서기
        else:
            start_service(t, t)            # 비어 있으면 바로 주문
    elif kind == 'order_done':
        schedule(t + expo(MAKE_MEAN), 'make_done', who)   # 주문이 끝나면 바로 제조
    elif kind == 'make_done':
        stays.append(t - who)              # 도착부터 커피 받을 때까지
        busy = False
        if queue:                          # ⑤ C 단계: 줄에 손님이 있으면 다음 손님
            start_service(t, queue.pop(0))

# ── 결과와 이론값(P-K 공식) 비교 ──
ES = ORDER_MEAN + MAKE_MEAN                          # 평균 서비스 시간 1.4분
ES2 = ORDER_MEAN**2 + MAKE_MEAN**2 + ES**2           # E[S²] = 분산 + 평균² (지수 분포 두 개의 합)
rho = LAM * ES
Wq_theory = LAM * ES2 / (2 * (1 - rho))
Wq = sum(waits) / len(waits)
print(f'가동률 ρ        이론 {rho:.3f}')
print(f'평균 줄 대기 Wq  이론 {Wq_theory:.3f}분   시뮬레이션 {Wq:.3f}분')
print(f'평균 체류 W      이론 {Wq_theory + ES:.3f}분   시뮬레이션 {sum(stays)/len(stays):.3f}분')
print(f'리틀의 법칙      Lq = {area_q/last_t:.3f}   λ·Wq = {LAM*Wq:.3f}')

        SimPy로 옮기기 심화

        이 페이지의 엔진과 위 코드는 사건 예약 관점입니다. 사건마다 상태를 어떻게 바꿀지 적습니다. SimPy는 프로세스 상호작용 관점입니다. 손님 한 명, 품목 하나가 겪는 일을 순서대로 적으면, 라이브러리가 그 흐름을 사건으로 쪼개 FEL에 넣어 줍니다. 같은 모델을 두 관점으로 보면 DES가 어떻게 돌아가는지 더 잘 보입니다.

        아래는 6단계 모델(머신과 배치 조리)을 키오스크 대신 계산 전담 1명 + 제조 2명으로 옮긴 것입니다. AllOf가 fork-join이고, 오븐은 기다리던 핫도그를 모아 한 번에 굽는 별도 프로세스입니다. 이 코드는 머신을 먼저 잡고 점원을 기다리므로, 둘이 동시에 비어야 시작하는 이 페이지 엔진과 결과가 조금 다릅니다. 그 차이가 왜 생기는지 설명해 보는 것도 좋은 연습입니다.

        import random, statistics as stats
import simpy

# ── 입력 데이터 (단위: 분) ─────────────────────────────────────────
# 품목: (점원 손 작업 시간, 필요한 머신, 머신 단독 가동 시간)
MENU = {'아메리카노': (1.0, 'esp', 0.0), '라떼': (2.0, 'esp', 0.0),
        '아이스티': (0.6, None, 0.0), '밀크쉐이크': (0.5, 'bl', 1.5),
        '핫도그': (0.5, 'oven', 0.0)}
MIX = [35, 25, 15, 10, 15]                     # 메뉴 비율 (MENU 순서와 같음)
N_DIST = {1: .50, 2: .28, 3: .14, 4: .08}      # 한 손님의 주문 개수 분포
LAM = 36 / 60                                  # 도착률 λ (명/분)
OVEN_CAP, OVEN_TIME = 4, 4.0                   # 오븐: 한 번에 4개, 4분


def draw(mean, cv=0.5):
    """작업 시간 하나를 뽑는다: 평균 mean, 변동계수 cv인 감마 분포."""
    k = 1 / cv**2                              # 모양 모수 k = 1/CV²
    return random.gammavariate(k, mean / k)


class Cafe:
    """카페의 자원(사람, 머신)과 오븐 프로세스를 담는 객체."""

    def __init__(self, env, makers=2, groups=2):
        self.env = env
        # Resource = 용량이 정해진 자원. 다 차면 request()가 FIFO 대기열에서 기다린다.
        self.cashier = simpy.Resource(env, 1)  # 계산 전담 1명 (창구 1개)
        self.maker = simpy.Resource(env, makers)              # 제조 점원
        self.machine = {'esp': simpy.Resource(env, groups),   # 에스프레소 그룹
                        'bl': simpy.Resource(env, 1)}         # 블렌더
        # Store = 물건을 넣고 꺼내는 대기열. 굽기를 기다리는 핫도그가 들어간다.
        self.oven_q = simpy.Store(env)
        env.process(self.oven())               # 오븐은 시뮬레이션 내내 도는 프로세스

    def oven(self):
        """배치 서버: 기다리는 핫도그를 최대 OVEN_CAP개까지 모아 한 번에 굽는다."""
        while True:
            batch = [(yield self.oven_q.get())]            # 하나가 들어올 때까지 대기
            while self.oven_q.items and len(batch) < OVEN_CAP:
                batch.append((yield self.oven_q.get()))    # 이미 기다리던 것 모두 태우기
            yield self.env.timeout(OVEN_TIME)              # 굽는 동안 시계가 OVEN_TIME만큼 진행
            for cooked in batch:
                cooked.succeed()               # 각 핫도그를 기다리던 프로세스를 깨운다

    def make(self, name):
        """품목 하나가 완성될 때까지의 흐름 (프로세스 상호작용 관점)."""
        hands, mach, alone = MENU[name]
        if mach == 'oven':
            cooked = self.env.event()          # "다 구워짐"을 알려 줄 사건
            yield self.oven_q.put(cooked)      # 오븐 대기열에 넣고
            yield cooked                       # 구워질 때까지 이 프로세스는 멈춤
            mach = None                        # 이후 마무리는 점원만 필요
        if mach:
            with self.machine[mach].request() as m:        # with 블록을 나오면 자동 반납
                yield m                        # ① 머신 확보 (비면 즉시, 아니면 대기)
                with self.maker.request() as p:
                    yield p                    # ② 점원 확보
                    yield self.env.timeout(draw(hands))    # 점원 + 머신 함께 작업
                if alone:                      # 점원은 반납, 머신만 계속 돈다 (블렌더)
                    yield self.env.timeout(draw(alone))
        else:
            with self.maker.request() as p:    # 머신이 필요 없는 품목
                yield p
                yield self.env.timeout(draw(hands))


def customer(env, cafe, log):
    """손님 한 명: 줄 서기 → 주문 → 품목 여러 개 동시 제조(fork) → 모두 받으면 떠남(join)."""
    arrive = env.now
    n = random.choices(list(N_DIST), list(N_DIST.values()))[0]   # 주문 개수
    items = random.choices(list(MENU), MIX, k=n)                 # 주문 품목
    with cafe.cashier.request() as r:
        yield r                                # 줄 대기: 창구가 빌 때까지
        start = env.now
        yield env.timeout(draw(0.3 + 0.1 * n)) # 주문(계산) 시간
    jobs = [env.process(cafe.make(it)) for it in items]   # fork: 품목마다 프로세스 생성
    yield simpy.AllOf(env, jobs)                          # join: 전부 끝나야 다음 줄로
    log.append(dict(arrive=arrive, wq=start - arrive, w=env.now - arrive,
                    n=n, hotdog='핫도그' in items))


def source(env, cafe, log):
    """도착 발생기: 지수 분포 간격(포아송 과정)으로 손님을 만든다."""
    while True:
        yield env.timeout(random.expovariate(LAM))
        env.process(customer(env, cafe, log))


def run(seed, warmup=30, horizon=480):
    """반복 1회: 워밍업을 버리고 8시간 동안의 평균을 돌려준다."""
    random.seed(seed)                          # 씨앗 고정 → 결과 재현 가능
    env, log = simpy.Environment(), []
    env.process(source(env, Cafe(env), log))
    env.run(until=warmup + horizon)            # 내부적으로 FEL에서 사건을 하나씩 꺼내 처리
    log = [c for c in log if c['arrive'] >= warmup]   # 초기 편향 제거
    # 추월: 나보다 늦게 온 누군가가 나보다 먼저 끝났는가 (뒤에서부터 최소 종료 시각 추적)
    log.sort(key=lambda c: c['arrive'])
    earliest_after, overtaken = float('inf'), 0
    for c in reversed(log):
        end = c['arrive'] + c['w']
        overtaken += earliest_after < end
        earliest_after = min(earliest_after, end)
    return (stats.mean(c['w'] for c in log),
            stats.mean(c['wq'] for c in log), overtaken / len(log))


# 독립 반복 20회 → 반복별 평균으로 95% 신뢰구간 계산
reps = [run(seed) for seed in range(20)]
for name, vals in zip(['평균 체류 W', '평균 줄 대기 Wq', '추월 비율'], zip(*reps)):
    m, s = stats.mean(vals), stats.stdev(vals)
    hw = 2.093 * s / len(vals) ** 0.5          # t(0.975, 19) = 2.093
    print(f'{name}: {m:.3f} ± {hw:.3f}')
