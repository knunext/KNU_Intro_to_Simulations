3-2LLM 에이전트와 시뮬레이션

3편의 여우와 토끼는 사람이 적은 if문으로 움직였습니다. 대화하고, 협상하고, 상황을 판단하는 에이전트는 if문으로 다 적기 어렵습니다. 그래서 에이전트의 판단을 대규모 언어 모델(LLM)에 맡기는 시도가 늘고 있습니다. 이 편은 그렇게 했을 때 시뮬레이션의 무엇이 깨지는지, 비용, 재현성, 출력 분석, 검증을 하나씩 살펴봅니다.

이 편을 마치면

  • LLM 에이전트의 관찰, 프롬프트, 파싱, 행동으로 이어지는 루프를 설계하고, 판단과 세계를 나눌 수 있습니다.
  • 호출 시점을 사건 기반으로 바꾸고 응답을 기록해, 비용과 재현성 문제를 줄일 수 있습니다.
  • LLM 샘플링이 출력 분산에 더하는 몫을 알고, 반복 실행과 비교 실험을 설계할 수 있습니다.
  • 프롬프트 민감성, 행동의 획일화 같은 타당성 위협을 알고 기준 모델과 비교해 점검할 수 있습니다.

1왜 LLM 에이전트인가

행동 규칙을 사람이 다 적을 수 없는 에이전트가 있습니다. LLM은 그 규칙을 대신 '상상'해 줄 수 있지만, 그 대가로 시뮬레이션이 원래 갖고 있던 성질 몇 가지를 잃습니다.

1.1if문으로 적기 어려운 판단

3편의 토끼는 "배고프면 풀로 간다, 여우가 보이면 도망간다"처럼 몇 줄의 규칙으로 충분했습니다. 하지만 커피점 손님이 친구에게 받은 메시지를 보고 계획을 바꾸거나, 협상 상대의 말투에 따라 양보 폭을 정하거나, 지휘관이 애매한 첩보를 놓고 방책을 고르는 판단은 규칙으로 옮기기 어렵습니다.

Park 등이 2023년에 발표한 Generative Agents 연구는 LLM으로 움직이는 에이전트 스물다섯 명이 사는 작은 마을을 만들었습니다. 에이전트들은 겪은 일을 기억 흐름에 쌓고, 가끔 그것을 되돌아보며(반성) 하루 계획을 세웠습니다. 에이전트 하나에게 파티를 열겠다는 생각만 심어 두었는데, 소문이 퍼지고 초대가 오가며 다른 에이전트들이 그 시각에 모이는 일이 나타났습니다. 규칙을 하나하나 적지 않아도 그럴듯한 사회적 행동이 생길 수 있다는 것을 보여 준 사례입니다.

1.2시뮬레이션 쪽에서 보면

에이전트의 결정 함수가 LLM 호출로 바뀌면, 앞의 편들에서 당연하게 여겼던 것들이 달라집니다.

확률적이고, 시드로 통제되지 않는다

LLM은 같은 질문에도 다른 답을 냅니다. 그런데 그 무작위성은 내 난수 생성기가 아니라 서버 쪽에 있어서, 시드를 고정해도 같은 실행을 다시 만들 수 없습니다(2.3절).

느리고 비싸다

규칙 하나는 나노초 단위로 평가되지만, LLM 호출은 초 단위로 걸리고 토큰마다 비용이 듭니다. 에이전트 천 명이 매 틱 판단하면 실행 한 번이 감당하기 어려워집니다(2.2절).

표현에 민감하다

같은 상황을 조금 다르게 적기만 해도 결정이 달라질 수 있습니다. 프롬프트가 곧 모델의 일부이므로, 프롬프트를 바꾸는 것은 모델을 바꾸는 것입니다(2.5절, 3.1절).

속을 들여다볼 수 없다

규칙은 읽고 고칠 수 있지만, LLM이 왜 그렇게 답했는지는 직접 검사할 수 없습니다. 검증은 행동을 관찰해 비교하는 방식으로 할 수밖에 없습니다(2.5절).

2이론

원칙은 하나입니다. LLM에게는 판단만 맡기고, 세계의 시간과 물리와 자원은 시뮬레이터가 쥡니다.

2.1에이전트 루프

  1. 관찰시뮬레이터가 에이전트에게 보이는 것만 골라 줍니다. 줄 길이, 받은 메시지, 남은 예산처럼 그 에이전트가 실제로 알 수 있는 정보입니다. 전지적인 정보를 주면 에이전트가 알 수 없는 것을 근거로 판단하게 됩니다.
  2. 프롬프트역할, 상황, 고를 수 있는 행동 목록, 답의 형식을 적습니다. 행동을 목록에서만 고르게 해야 시뮬레이터가 결과를 계산할 수 있습니다.
  3. 호출과 파싱응답에서 행동을 읽어 냅니다. 형식을 어긴 응답은 반드시 생기므로, 다시 묻거나 정해 둔 기본 행동을 쓰는 규칙이 필요하고, 그런 일이 몇 번 있었는지 기록합니다.
  4. 행동과 결과시뮬레이터가 그 행동의 결과를 계산합니다. "떠남"을 골랐으면 떠나고, "공격"을 골랐으면 교전 판정은 시뮬레이터의 규칙이 합니다. LLM이 결과까지 정하게 두면 세계의 일관성이 무너집니다.
  5. 기억에이전트가 겪은 일을 다음 프롬프트에 요약해 넣습니다. 기억이 길어지면 관련 있는 것만 골라 넣는 검색과 요약이 필요합니다.

2-2편에서DEVS 원자 모델로 보면 LLM 호출은 δext 안에 들어갑니다. 입력 메시지(관찰)가 오면 LLM에게 물어 새 상태와 다음 출력(행동)을 정합니다. 시간 전진 ta와 결합은 그대로 시뮬레이터 몫입니다.

2.2언제 부를까

3편처럼 매 틱 모든 에이전트에게 물으면 호출 수는 에이전트 수 × 틱 수입니다. 그런데 대부분의 틱에서 에이전트는 하던 일을 계속할 뿐입니다. 2편과 2-2편의 생각을 빌려, 판단이 필요한 사건이 일어날 때만 묻고(손님이 도착했을 때, 메시지를 받았을 때) 나머지는 규칙으로 처리하면 호출이 크게 줄어듭니다. 같은 상황에 대한 답을 저장해 두고 다시 쓰면 더 줄어듭니다.

호출 수와 시간 어림

세 가지 호출 방식의 실행 한 번당 호출 수(로그 눈금)와, 반복 실행까지 포함한 총량입니다.

사건 기반으로 바꾸는 것만으로 호출이 '판단이 필요한 틱'의 비율만큼 줄어듭니다. 응답 재사용은 더 조심해야 합니다. 같은 상황에 같은 답을 재사용하면 에이전트들이 모두 같은 성격이 되어 버리기 때문입니다. 재사용할 때는 에이전트의 개성(페르소나)까지 키에 넣는 것이 보통입니다.

2.3재현성: 시드가 통제하지 못하는 것

0편에서 시드를 고정하면 같은 실행을 다시 만들 수 있다고 배웠습니다. LLM이 들어가면 그 약속이 깨집니다. 응답의 샘플링은 서버에서 일어나고, 서비스 쪽에서 모델이 갱신되기도 하며, 샘플링 온도(temperature)를 0으로 두어도 서버의 병렬 계산 때문에 드물게 다른 답이 나올 수 있습니다.

아래는 세계(도착 시각과 제조 시간)를 시드로 완전히 고정하고, 판단만 LLM 대역에게 맡긴 커피점을 다섯 번 돌린 결과입니다. 줄이 길수록 떠날 확률이 높아지는 손님입니다.

같은 세계, 다섯 번의 실행

선 하나가 실행 하나이고, 시간에 따라 떠난 손님 수를 누적했습니다.

온도

재현성을 되찾는 가장 확실한 방법은 기록하고 재생하는 것입니다. 프롬프트와 응답을 모두 저장해 두면, 같은 실행을 언제든 LLM 없이 그대로 다시 만들 수 있습니다. 모델 이름과 버전, 온도, 프롬프트 원문도 함께 남깁니다. 이 기록은 결과를 보고할 때 시드와 코드 버전을 남기는 것(5편)과 같은 역할을 합니다.

2.4출력 분석이 달라지는 점

출력의 흔들림에 원천이 하나 더 생깁니다. 세계의 난수에서 오는 분산과 LLM 샘플링에서 오는 분산입니다. 5편의 신뢰구간 공식은 그대로 쓰면 되지만, 실행마다 호출 비용이 드니 필요한 반복 횟수 n ≈ (1.96 S/ε)²가 곧 예산이 됩니다.

두 대안을 비교할 때 쓰는 공통 난수(5편 2.6절)도 절반만 통합니다. 세계의 난수는 두 대안에 똑같이 줄 수 있지만 LLM의 응답은 그럴 수 없습니다. 판단 결과가 비교의 대상이 아니라면 기록된 응답을 두 대안에 똑같이 재생해 변동을 줄일 수 있고, 판단 자체가 비교 대상이라면 반복을 더 늘려야 합니다.

2.5검증과 타당성

그럴듯하게 행동한다는 것과 타당하다는 것은 다릅니다. LLM 에이전트에는 규칙 기반 에이전트에 없던 위협이 있습니다.

프롬프트 민감성
같은 상황을 다르게 적으면 결정이 달라집니다. 결과가 상황 때문인지 표현 때문인지 구분해야 합니다. 의미가 같은 프롬프트 여러 개로 돌려 결론이 유지되는지 보는 것이 8편의 민감도 분석에 해당합니다.
획일화
LLM은 평균적인 답을 내는 경향이 있어 손님 백 명이 모두 비슷한 성격이 되기 쉽습니다. 실제 사람들의 행동 분포(참을성의 퍼짐 같은)와 비교해야 합니다.
편향과 기억
학습한 글에 많이 나온 행동 쪽으로 치우칠 수 있고, 유명한 시나리오는 그 결말을 '기억'해서 답할 수도 있습니다.
기준 모델
같은 시뮬레이터에서 판단만 단순한 규칙으로 바꾼 기준 모델과 비교합니다. LLM이 그 차이만큼의 가치를 더하는지가 질문입니다.
사람과 비교
가능하면 실측 데이터나 사람을 대상으로 한 실험 결과와 행동 분포를 비교합니다. 전문가에게 기록된 판단을 보여 주고 그럴듯한지 묻는 것(8편의 대면 타당성)도 도움이 됩니다.

3예제와 사례 연구

3.1줄을 보고 떠나는 손님

2편의 "붐비면 포기"를 세 가지 판단 방식으로 돌려 봅니다. 규칙 기반 손님은 각자 참을성(3~7명)이 있어 줄이 그 이상이면 떠납니다. LLM 대역 손님은 "지금 줄에 q명이 서 있습니다"라는 프롬프트 A와, 같은 상황을 "앞에 q명이나 기다리고 있습니다"라고 적은 프롬프트 B를 받습니다. 세계의 시드 30개마다 하루씩, 모두 같은 세계에서 돌립니다.

판단 방식에 따른 하루 이탈률

점 하나가 하루치 실행이고, 굵은 막대는 평균과 95% 신뢰구간입니다.

LLM 온도

프롬프트 B는 상황을 하나도 바꾸지 않았는데 이탈률이 높습니다. 날마다의 흔들림이 커서 두 구간이 겹쳐 보일 수 있지만, 같은 세계의 날끼리 짝지어 차이를 보면(5편의 공통 난수) 그 차이는 분명히 0보다 큽니다. 이 모델로 "대기 공간을 늘리면 이탈이 얼마나 줄까"를 묻는다면, 답이 프롬프트의 말투에 따라 달라진다는 뜻입니다. 온도를 바꿔도 이탈률의 수준이 달라집니다. 온도 역시 판단 규칙의 일부라는 뜻이므로 결과와 함께 보고해야 합니다. 이 예에서는 날마다의 흔들림 대부분이 손님 도착의 무작위성에서 오지만, 판단의 무작위성이 큰 모델일수록 같은 정밀도에 더 많은 반복이 필요합니다. 대역의 수치는 설명을 위해 정한 것이지만, 실제 LLM에서도 표현에 따라 결정이 흔들리는 일은 흔합니다.

3.2파이썬 에이전트 루프

호출을 감싸는 정책 객체 하나에 캐시, 파싱, 실패 시 기본 행동, 기록을 모았습니다. fake_llm 자리에 실제 API를 부르는 함수를 넣으면 그대로 동작합니다. 판단은 손님이 도착하는 사건에서만 묻습니다.

# llm_agents.py : 커피점 손님의 '기다릴까, 떠날까'를 LLM에게 묻는 에이전트 루프
import hashlib, heapq, json, math, random, re

PROMPT = ("당신은 커피점에 막 도착한 손님입니다. 지금 줄에 {q}명이 서 있습니다. "
          "기다릴지 떠날지 정하세요. 답은 '기다림' 또는 '떠남' 한 단어로만 하세요.")

def fake_llm(prompt, temperature=0.7, rng=random.Random()):
    """실제 API 대신 쓰는 대역. 줄이 길수록 '떠남'이 많아지고, 가끔 형식을 어긴다.
    rng에는 일부러 시드를 주지 않았다. API의 샘플링처럼 우리가 통제할 수 없는 무작위성이다."""
    q = int(re.search(r"(\d+)명", prompt).group(1))
    p_leave = 1 / (1 + math.exp(-(q - 5) / max(temperature, 1e-3)))
    if rng.random() < 0.03:
        return "음... 상황에 따라 다를 것 같아요."          # 형식을 어긴 응답
    return "떠남" if rng.random() < p_leave else "기다림"

class LLMPolicy:
    """LLM 호출을 감싼다: 캐시, 파싱, 실패 시 기본 행동, 기록."""
    def __init__(self, call, cache=None):
        self.call, self.cache, self.log = call, cache if cache is not None else {}, []
        self.calls = self.parse_fail = 0
    def decide(self, agent_id, obs):
        prompt = PROMPT.format(**obs)
        key = hashlib.sha256(f"{agent_id}|{prompt}".encode()).hexdigest()[:16]
        if key in self.cache:                        # 같은 손님, 같은 상황이면 기록된 답을 재생
            action = self.cache[key]
        else:
            self.calls += 1
            text = self.call(prompt)
            m = re.search(r"기다림|떠남", text)
            if m is None:
                self.parse_fail += 1
            action = m.group(0) if m else "기다림"   # 형식이 틀리면 정해 둔 기본 행동
            self.cache[key] = action
        self.log.append({"agent": agent_id, "prompt": prompt, "action": action})
        return action

def run_day(policy, seed, lam=1.2, mean_svc=1.0, minutes=120):
    """세계(도착, 제조 시간)는 시드로 고정. 판단은 손님이 도착하는 사건에서만 묻는다."""
    rng = random.Random(seed)
    fel, t, i = [], 0.0, 0
    while True:
        t += rng.expovariate(lam)
        if t > minutes: break
        heapq.heappush(fel, (t, "arr", i, rng.expovariate(1 / mean_svc))); i += 1
    queue, busy, left = [], False, 0
    while fel:
        t, kind, cid, svc = heapq.heappop(fel)
        if kind == "arr":
            if policy.decide(cid, {"q": len(queue)}) == "떠남":
                left += 1
                continue
            if busy: queue.append(svc)
            else: busy = True; heapq.heappush(fel, (t + svc, "dep", cid, 0))
        else:
            if queue: heapq.heappush(fel, (t + queue.pop(0), "dep", cid, 0))
            else: busy = False
    return left, i

# 1) 기록 없이 같은 세계를 세 번: 결과가 매번 다르다
for k in range(3):
    pol = LLMPolicy(lambda p: fake_llm(p))
    left, n = run_day(pol, seed=42)
    print(f"실행 {k + 1}: 손님 {n}명 중 {left}명 떠남, LLM 호출 {pol.calls}번, 형식 오류 {pol.parse_fail}번")

# 2) 첫 실행의 응답을 저장하고 재생: 결과가 똑같다
first = LLMPolicy(lambda p: fake_llm(p))
a = run_day(first, seed=42)
json.dump(first.cache, open("responses.json", "w", encoding="utf-8"), ensure_ascii=False)
replay = LLMPolicy(lambda p: fake_llm(p), cache=json.load(open("responses.json", encoding="utf-8")))
b = run_day(replay, seed=42)
print(f"기록한 실행 {a[0]}명 떠남, 재생한 실행 {b[0]}명 떠남, 재생 중 새 호출 {replay.calls}번")

3.3워게임과 지휘결심 사례

LLM을 지휘관이나 참모 역할로 넣은 워게임 연구가 빠르게 늘고 있습니다. Rivera 등의 연구(FAccT 2024)는 국가를 대표하는 에이전트들을 여러 LLM으로 움직이는 외교·군사 워게임을 만들고 행동을 점수로 평가했습니다. 연구진은 조사한 다섯 모델 모두에서 긴장을 고조시키는 경향과 예측하기 어려운 급격한 고조가 나타났고, 군비 경쟁 같은 흐름과 드물게는 핵무기 사용까지 관찰되었다고 보고했습니다.

이 연구에서 시뮬레이션을 공부하는 사람이 가져갈 교훈은 둘입니다. 첫째, 이런 결과는 "그 모델과 그 프롬프트가 이 시나리오에서 어떻게 행동하는가"에 대한 실험이지, 사람 지휘관이 어떻게 행동할지에 대한 예측이 아닙니다. 둘째, 그렇기 때문에 반복 실행, 프롬프트 변형, 기준 모델 비교, 전문가 검토가 결과 해석의 일부가 되어야 합니다.

구조로 보면 2.1절의 원칙이 그대로 적용됩니다. 지형, 이동, 교전 판정, 시간은 규칙과 물리에 기반한 시뮬레이터(2-2편의 부품들)가 맡고, LLM은 관찰 메시지를 받아 명령 메시지를 내놓는 '방책 선택' 부품 하나로 들어갑니다. 그러면 같은 시나리오를 사람 지휘관, 규칙 기반 지휘관, LLM 지휘관으로 바꿔 가며 같은 조건에서 비교할 수 있습니다.

4연결과 정리

4.1앞뒤 편과의 연결

3편에서규칙 기반 에이전트는 이 편의 기준 모델입니다. LLM 에이전트를 만들기 전에 같은 시뮬레이터에서 규칙 기반 버전부터 돌려 두세요.

2-2편에서LLM 호출을 원자 모델의 δext 안에 두면, 판단 부품만 갈아 끼우며 비교할 수 있습니다.

4편으로기록한 프롬프트와 응답은 그 자체로 데이터입니다. 행동의 분포를 추정하면, 다음에는 LLM 대신 그 분포에서 뽑는 값싼 대리 모델을 쓸 수도 있습니다.

5편과 8편으로반복 횟수는 곧 예산이고, 프롬프트를 바꿔 보는 것은 민감도 분석입니다.

4.2요약

원칙
LLM은 판단만. 시간, 물리, 자원, 결과 판정은 시뮬레이터가.
루프
관찰 → 프롬프트(행동 목록, 형식) → 호출 → 파싱과 기본 행동 → 결과 → 기억.
비용
매 틱 대신 사건 기반으로 묻기. 재사용은 개성을 키에 넣어서.
재현성
시드로는 안 된다. 프롬프트와 응답, 모델 버전, 온도를 기록하고 재생.
출력 분석
분산의 원천이 둘. 반복 횟수가 예산. 공통 난수는 세계 쪽만.
타당성
프롬프트 민감성, 획일화, 편향. 기준 모델, 사람 데이터, 전문가와 비교.

4.3연습 문제

1. 에이전트 500명이 1,000틱 동안 매 틱 LLM에게 묻는 모델을, 판단이 필요한 틱이 평균 2%뿐이라는 사실을 이용해 바꾸면 호출은 몇 번이 될까요?

매 틱이면 500 × 1,000 = 50만 번, 사건 기반이면 2%인 1만 번입니다. 응답 시간이 2초이고 동시에 16개를 보낼 수 있다면 실행 한 번이 약 17시간에서 약 21분으로 줄어듭니다.

2. 온도 0으로 두었는데도 같은 실험의 결과가 가끔 다릅니다. 무엇을 의심하고, 어떻게 해야 할까요?

서버 쪽 병렬 계산의 비결정성이나 모델 갱신을 의심할 수 있습니다. 어느 쪽이든 내가 통제할 수 없으므로, 프롬프트와 응답을 모두 기록하고 분석과 재현은 기록을 재생해서 합니다. 모델 이름과 버전도 함께 남깁니다.

3. 3.1절에서 대기 공간을 늘리는 대안의 효과를 LLM 손님으로 평가하려 합니다. 프롬프트 민감성에 대해 무엇을 해야 할까요?

의미가 같은 프롬프트를 여러 개 준비해 각각으로 두 대안을 비교하고, 대안의 효과(차이)가 프롬프트에 상관없이 같은 방향인지 확인합니다. 이탈률의 수준은 프롬프트마다 달라도, 차이의 방향과 크기가 유지되면 결론을 더 믿을 수 있습니다. 규칙 기반 기준 모델의 결과도 함께 보고합니다.

4. 교전 판정까지 LLM에게 "그래서 누가 이겼는지 말해 줘"라고 맡기면 어떤 문제가 생길까요?

세계의 규칙이 실행마다, 표현마다 달라집니다. 같은 사격이 어떤 때는 명중하고 어떤 때는 빗나가는데 그 이유를 검증할 수 없고, 화력과 거리 같은 모델의 입력을 바꿔도 결과가 일관되게 반응하지 않습니다. 판정은 검증 가능한 규칙(시뮬레이터)에 두어야 합니다.
