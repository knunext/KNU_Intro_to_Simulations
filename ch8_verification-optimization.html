8검증, 타당성, 최적화

시뮬레이션이 그럴듯한 숫자를 내놓는다고 해서 믿을 수 있는 것은 아닙니다. 프로그램이 의도대로 도는지(검증), 모델이 현실을 충분히 닮았는지(타당성 확인), 어떤 입력이 결론을 좌우하는지(민감도 분석)를 확인한 뒤에야, 시뮬레이션으로 가장 좋은 운영 방안을 찾는(최적화) 일을 할 수 있습니다.

이 편을 마치면

  • 검증과 타당성 확인을 구분하고, 버그를 잡는 체계적인 점검을 할 수 있습니다.
  • 시뮬레이션 출력과 실측 데이터를 통계적으로 비교하고, 보정과 과적합의 관계를 압니다.
  • 민감도 분석으로 결론을 좌우하는 입력을 찾을 수 있습니다.
  • 잡음이 있는 목적함수를 공통 난수와 지역 탐색으로 최적화할 수 있습니다.

1왜 확인이 먼저인가

시뮬레이션의 가장 큰 위험은 틀린 답이 아니라, 틀렸다는 것을 아무도 모르는 그럴듯한 답입니다.

1.1그럴듯한 틀린 답

한 학생이 커피점 모델을 만들어 “점심에 직원 3명은 필요 없고 2명이면 충분하다”는 결론을 냈습니다. 평균 대기 2분, 그래프도 깔끔했습니다. 그런데 코드를 보니, 줄이 10명을 넘으면 새 손님이 기록 없이 사라지고 있었습니다. 가장 오래 기다릴 손님들이 통계에서 빠져 있었던 겁니다.

이런 오류는 결과 그래프만 봐서는 드러나지 않습니다. 숫자가 이상하게 크거나 작지 않기 때문입니다. 그래서 시뮬레이션 결과를 쓰기 전에 체계적으로 의심하는 절차가 필요합니다. 3.1절에서 이 버그를 직접 찾아봅니다.

1.2세 가지 질문

검증 (verification)

“모델을 올바르게 만들었는가?” 프로그램이 개념 모델대로 동작하는지 확인합니다. 버그 찾기입니다.

타당성 확인 (validation)

“올바른 모델을 만들었는가?” 모델이 이 질문에 답할 만큼 현실을 닮았는지 확인합니다. 현실과의 비교입니다.

신뢰 (credibility)

“결정권자가 이 모델을 믿고 쓰는가?” 사장님이 애니메이션을 보며 “우리 가게 같다”고 느끼는 것도 중요합니다. 하지만 앞의 둘을 대신하지는 못합니다.

2이론

모델은 “맞다”가 아니라 “이 목적에 충분히 쓸 만하다”고 판정됩니다. 그 판정을 뒷받침하는 증거를 모으는 방법들입니다.

2.1사전트의 틀

시뮬레이션 연구에는 세 가지 대상이 있습니다. 현실 시스템, 그것을 종이에 단순화한 개념 모델, 그리고 그것을 코드로 옮긴 컴퓨터 모델입니다. 확인 작업은 이 셋을 잇는 화살표마다 따로 있습니다. 화살표를 눌러 보세요.

2.2검증 기법

실행 추적
손님 몇 명의 사건을 한 줄씩 출력해 손으로 따라가 봅니다. 2편의 사건 로그 패널이 이 도구입니다. 가장 원시적이지만 가장 많은 버그를 잡습니다.
보존 법칙
시뮬레이션이 끝났을 때 “들어온 수 = 나간 수 + 아직 안에 있는 수”가 성립해야 합니다. SIR의 S + I + R = N도 같은 종류입니다(6편).
리틀의 법칙
시간 평균으로 잰 시스템 내 인원 L과, 도착률 λ × 손님별 평균 체류 W가 같아야 합니다. 모델 구조와 상관없이 성립하므로 거의 모든 대기 시스템에 쓸 수 있는 강력한 점검입니다(1편).
극한 조건
손님이 거의 안 오면 대기는 0에 가까워야 하고, 직원이 무한히 많아도 마찬가지입니다. 도착률이 처리 능력을 넘으면 줄이 끝없이 늘어야 합니다.
공식과 비교
모델을 공식이 있는 특수한 경우(지수분포 도착과 처리, M/M/c)로 단순화해 돌린 결과가 공식값과 맞는지 봅니다. 2편 1단계의 P-K 공식 검증이 이것입니다.

2.3타당성 확인: 현실과 비교하기

가장 직접적인 방법은 같은 조건에서 시뮬레이션 출력과 실측 출력을 비교하는 것입니다. 예를 들어 실제로 10일간 점심 평균 대기를 쟀다면, 시뮬레이션도 여러 날 돌려 두 평균의 차이에 대한 신뢰구간을 만듭니다. 두 집단의 분산이 다를 수 있으므로 웰치 방식을 씁니다.

“차이가 없다”를 증명할 수는 없습니다. 실측 데이터가 3일뿐이면 구간이 넓어서 거의 모든 모델이 통과합니다. 그래서 통계 검정과 함께 “차이가 얼마까지면 결정에 문제가 없는가”라는 실용적 기준을 미리 정합니다. 예: “평균 대기의 차이가 ±1분 이내면 쓸 만하다”. 구간 전체가 이 범위 안에 들어와야 합격입니다. 평균뿐 아니라 대기시간 분포 전체(4편의 Q-Q 그림), 시간대별 패턴도 비교하세요.

2.4보정과 과적합

모델과 현실이 다르면 모수를 조정해 맞추고 싶어집니다. 이것이 보정(calibration)입니다. 6편에서 배스 모델의 p, q를 데이터에 맞춘 것처럼요. 하지만 조절 손잡이가 많으면 무엇이든 맞출 수 있습니다. 모델이 현실의 구조가 아니라 데이터의 우연까지 외워 버리는 과적합입니다.

해결책은 머신러닝과 같습니다. 데이터를 나눠, 일부(보정용)로 모수를 맞추고 보정에 쓰지 않은 나머지(검증용)로 타당성을 확인합니다. 특히 검증용 데이터는 조건이 다른 날(손님이 많은 시험 기간 등)이면 더 좋습니다. 모델이 정말 구조를 잡았다면 조건이 바뀌어도 맞아야 하니까요. 3.2절에서 직접 해 봅니다.

2.5민감도 분석

입력 하나를 조금 바꿨을 때 출력이 얼마나 변하는지 봅니다. 출력을 크게 흔드는 입력은 더 정확히 측정해야 하고(4편), 결론이 그 입력의 그럴듯한 범위 안에서 뒤집히지 않는지 확인해야 합니다. 입력마다 ±20%씩 바꿔 출력 변화를 막대로 쌓은 그림이 회오리처럼 보여서 토네이도 그림이라고 부릅니다.

커피점 평균 대기의 토네이도 그림

기준: 분당 0.6명, 바리스타 2명, 평균 제조 3분, 제조 시간 변동계수 0.5, 주문 받는 시간 0.3분. 각 입력을 하나씩 바꿔 공통 난수로 30일씩 돌렸습니다. 막대 왼쪽 끝은 입력을 줄였을 때, 오른쪽 끝은 늘렸을 때입니다.

한계: 하나씩 바꾸는 민감도 분석은 입력끼리의 상호작용을 놓칩니다. 상호작용이 중요하면 5편의 요인 설계를 쓰거나, 모든 입력을 동시에 분포에서 뽑아 수백 번 돌리는 몬테카를로 민감도 분석을 합니다.

2.6시뮬레이션 최적화

모델을 믿을 수 있게 되면 “어떻게 하는 것이 가장 좋은가”를 물을 수 있습니다. 결정 변수(시간대별 직원 수)를 정하면 시뮬레이션이 성과(대기)를 알려 주고, 이를 비용으로 바꿔 최소화합니다.

결정 변수가 10개 시간대 × 직원 1~6명이면 조합이 610 ≈ 6천만 개라 모두 돌려 볼 수는 없습니다. 실무에서는 다음 같은 탐색법을 씁니다.

지역 탐색 (언덕 오르기)
지금 근무표에서 한 시간대의 직원을 ±1 해 보고, 나아지면 받아들이기를 반복합니다. 단순하고 빠르지만 지역 최적에 갇힐 수 있습니다.
무작위 재시작, 담금질
여러 출발점에서 다시 하거나, 가끔은 나빠지는 쪽으로도 움직여 지역 최적을 벗어납니다.
순위 선택 (R&S)
후보가 수십 개 이내면 모두 돌리되, 가망 없는 후보는 일찍 탈락시키고 좋은 후보에 반복 실행을 몰아줍니다.
대리 모델
시뮬레이션 결과로 빠른 근사 함수(회귀, 가우시안 과정)를 학습해 탐색 방향을 정합니다. 시뮬레이션 한 번이 아주 비쌀 때 씁니다.

3예제와 사례 연구

버그 찾기, 실측 데이터로 보정과 타당성 확인, 그리고 확인을 마친 모델로 근무표를 최적화하는 순서로 진행합니다.

3.1버그 찾기쉬움

바리스타 2명인 커피점(M/M/2, 분당 0.6명, 평균 3분) 모델이 네 가지 버전으로 있습니다. 하나는 올바르고 셋에는 서로 다른 버그가 숨어 있습니다. 점검 버튼을 눌러 어느 버전에 어떤 문제가 있는지 찾아보세요. 각 점검은 손님 2만 명을 시뮬레이션합니다.

네 버전, 네 가지 점검

모델 버전

정답 보기

A는 올바른 모델입니다. B는 두 직원이 모두 바쁠 때 새 손님을 늘 0번 직원 뒤에 세웁니다(1번이 먼저 비어도 기다림). 리틀의 법칙과 보존 법칙은 통과하지만 공식과 비교하면 대기가 너무 깁니다. 겉으로 일관된 잘못된 논리는 보편 법칙만으로는 잡히지 않는다는 교훈입니다. C는 대기시간을 기록할 때 앞 손님의 도착 시각을 씁니다(한 칸 밀림). 손님 기록과 시간 평균이 어긋나서 리틀의 법칙에서 걸립니다. D는 1.1절의 그 버그입니다. 줄이 10명을 넘으면 손님이 기록 없이 사라집니다. 보존 법칙에서 걸리고, 대기가 공식보다 짧게 나옵니다.

3.2실측 데이터로 보정하고 확인하기중간

점심 시간대(12~13시) 평균 대기를 평소 7일, 시험 기간 3일 동안 쟀습니다(가상 데이터). 모델의 불확실한 입력은 평균 제조 시간입니다. 처음 측정한 3분이 맞는지 모르겠습니다. 평소 7일(보정용)에 맞도록 제조 시간을 조정한 뒤, 시험 기간 3일(검증용, 손님이 20% 많음)에서도 맞는지 확인하세요.

보정과 검증

점: 실측. 막대: 시뮬레이션 40일의 평균과 95% 구간. 아래 표는 2.3절 방식의 차이 구간입니다.

보정용 데이터에 맞추고 나면 검증용 데이터에서도 차이 구간이 실용 기준(±1분) 안에 들어오는지 보세요. 들어온다면 모델이 “손님이 늘면 대기가 어떻게 변하는가”라는 구조를 제대로 잡았다는 증거가 됩니다. “손잡이 하나 더”를 켜면 시험 기간 데이터에도 따로 맞출 수 있는데, 그러면 검증용 데이터를 보정에 써 버린 것이라 더 이상 독립적인 확인이 되지 못합니다. 손잡이를 늘려 맞추는 것은 쉽지만, 그만큼 확인할 수 있는 것이 줄어듭니다.

3.3시간대별 근무표 최적화실전

확인을 마친 모델로 하루 근무표를 짭니다. 08~18시 10개 시간대마다 바리스타를 1~6명 배치합니다. 손님은 4편 2.7절의 평소 학기 패턴으로 오고, 평균 제조 시간은 3분, 시급은 1만 원입니다. 막대를 눌러 직원 수를 바꾸거나(위쪽 절반은 +1, 아래쪽 절반은 −1), 지역 탐색을 돌려 보세요.

근무표와 비용

막대: 시간대별 직원 수. 선: 시간당 도착률. 오른쪽: 지역 탐색의 진행(비용).

공통 난수를 끄고 지역 탐색을 돌려 보세요. 평가할 때마다 다른 손님 흐름을 쓰므로, 운 좋은 날 나온 낮은 비용에 속아 실제로는 나쁜 이동을 받아들이곤 합니다. 진행 그래프가 들쭉날쭉하고 최종 근무표도 실행할 때마다 달라집니다. 공통 난수를 켜면 모든 후보가 같은 손님 흐름에서 비교되므로 탐색이 안정적입니다. 다만 공통 난수로 고른 답은 그 특정 손님 흐름에 맞춰졌을 수 있으므로, 마지막에 새로운 난수로 반복 실행해 비용을 다시 평가하는 것이 원칙입니다(5편).

실제로 적용하려면 여기서 끝이 아닙니다. 새 근무표를 2주 정도 시범 운영하며 대기를 다시 재고, 예측과 비교해 모델을 다시 보정합니다. 모델과 현실 사이를 이렇게 반복하며 오가는 것이 시뮬레이션이 실제 의사결정에 쓰이는 방식이며, 이 고리를 계속 자동으로 돌리면 디지털 트윈이 됩니다.

import numpy as np

RATE = [50, 45, 32, 35, 80, 60, 37, 40, 30, 18]       # 08~18시 시간당 도착률 (예시)

def day_cost(staff, seed, wage=10000, cw=150, mean_service=3.0):
    """근무표 staff(시간대별 직원 수)로 하루를 돌려 비용을 돌려준다."""
    rng = np.random.default_rng(seed)                  # 같은 seed = 같은 손님 흐름 (공통 난수)
    t, free, total_wait = 0.0, [0.0] * max(staff), 0.0
    lam_max = max(RATE) / 60
    while True:
        t += rng.exponential(1 / lam_max)              # 솎아내기로 시간대별 도착 (4편)
        if t >= 600:
            break
        if rng.random() > RATE[int(t // 60)] / 60 / lam_max:
            continue
        s = mean_service * rng.gamma(4, 1 / 4)
        best = None
        for j in range(len(free)):                     # 근무 중인 직원 중 가장 먼저 시작할 수 있는 사람
            start = max(t, free[j])
            while start < 600 and staff[int(start // 60)] <= j:
                start = (start // 60 + 1) * 60
            if best is None or start < best[0]:
                best = (start, j)
        start, j = best
        total_wait += start - t
        free[j] = start + s
    return wage * sum(staff) + cw * total_wait

def local_search(staff, seeds):
    cost = lambda x: np.mean([day_cost(x, s) for s in seeds])
    best, best_c, improved = list(staff), cost(staff), True
    while improved:
        improved = False
        for h in range(len(best)):
            for d in (-1, 1):
                x = list(best); x[h] += d
                if 1 <= x[h] <= 6 and (c := cost(x)) < best_c:
                    best, best_c, improved = x, c, True
    return best, best_c

plan, c = local_search([3] * 10, seeds=range(10))
fresh = np.mean([day_cost(plan, s) for s in range(1000, 1030)])   # 새 난수로 재평가
print(plan, f"탐색 중 {c:,.0f}원, 재평가 {fresh:,.0f}원")

검증
코드가 개념 모델대로인가. 추적, 보존, 리틀의 법칙, 극한 조건, 공식 비교를 여러 개 함께.

출력이 현실과 맞는가. 차이 구간 + 실용 기준. 평균뿐 아니라 분포와 패턴도.
보정

민감도
토네이도 그림과 탄력성. 결론을 좌우하는 입력을 더 정확히 잰다.
최적화
잡음 있는 목적함수. 공통 난수로 비교하고, 고른 답은 새 난수로 다시 평가한다.

4.3연습 문제

1. 리틀의 법칙 점검을 통과했습니다. 이제 모델에 버그가 없다고 말할 수 있을까요?

아닙니다. 리틀의 법칙은 거의 모든 대기 시스템에서 성립하므로, 논리가 잘못되었지만 일관된 모델(3.1절의 B)도 통과합니다. 필요조건이지 충분조건이 아닙니다. 여러 점검을 함께 쓰고, 특히 공식이 있는 특수한 경우와 비교하세요.

2. 실측 3일과 시뮬레이션 1000일을 비교한 차이 구간이 −4분 ~ +5분이었습니다. 모델이 타당하다고 할 수 있나요?

통계적으로 기각되지 않았을 뿐, 타당하다는 증거는 아닙니다. 구간이 실용 기준(예: ±1분)보다 훨씬 넓습니다. 실측 날 수를 늘려야 하고, 시뮬레이션 반복을 늘리는 것은 도움이 거의 안 됩니다(폭을 실측 쪽이 좌우하기 때문).

3. 토네이도 그림에서 도착률 ±20%가 대기 −50%~+150%를 만들었습니다. 무엇을 해야 할까요?

도착률의 탄력성이 매우 큽니다. 도착률을 더 정확히(더 많은 날, 시간대별로) 측정해야 하고, 결론(예: 직원 수)이 도착률의 그럴듯한 범위 전체에서 유지되는지 확인해야 합니다. 유지되지 않는다면 “도착률이 이 값 이상이면 3명” 같은 조건부 결론으로 보고합니다.

4. 지역 탐색으로 찾은 근무표의 비용이 탐색 중에는 52만 원이었는데, 새 난수로 다시 평가하니 56만 원이었습니다. 왜 그럴까요?

탐색은 같은 난수(공통 난수)에서 가장 좋아 보이는 답을 고르므로, 그 특정 손님 흐름에 운 좋게 맞는 답이 뽑히는 선택 편향이 생깁니다. 새 난수로의 재평가가 실제 성능에 대한 편향 없는 추정입니다. 그래서 최종 보고는 재평가 값으로 합니다.
